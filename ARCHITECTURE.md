# Architecture

Nibblets are self-hosted, always-on agents, each drawn as a hamster you can dress up. A nibblet is a thread: it runs in its own Docker container on one of three harnesses (Claude Agent SDK, Codex, OpenCode), wakes on a heartbeat and on schedules, keeps its memory outside the container in Postgres with pgvector, and can spawn sub-agents, which are child nibblets that run in their parent's container.

## Processes

Everything runs in Docker on two networks. `nibblet` has the database, the server and the credential proxy. `nibblet-runners` has the server, the credential proxy and the nibblets' containers, so a nibblet can't reach the database.

| Service        | Image                          | Address on the network | What it does                                                                                                                |
| -------------- | ------------------------------ | ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `server`       | `nibblet/server`               | `server:8420`          | API, web UI, live WebSocket, runner WebSocket, nibblet tools over MCP, scheduler, heartbeats, Docker orchestration, tunnels |
| `db`           | `pgvector/pgvector:0.8.7-pg18` | `db:5432`              | All durable state: nibblets, thread items, schedules, memories (with embeddings), peers, sign-ins                           |
| `credproxy`    | `nibblet/credproxy`            | `credproxy:8787`       | Holds the host's Claude and ChatGPT subscription credentials, refreshes them, and injects them into harness traffic         |
| `tunnel`       | `cloudflare/cloudflared`       | none                   | Started by the server when a tunnel is configured                                                                           |
| `nibblet-<id>` | `nibblet/runner`               | `nibblet-<id>`         | One per running nibblet: the runner, its harness, OpenComputerUse with Chromium, and the desktop for its other apps         |

The server is the only service published on the host (`127.0.0.1:8420`). It mounts the Docker socket to manage the tunnel and runner containers.

## Credentials (`apps/credproxy`)

Runner containers never see a Claude or ChatGPT subscription token. (What they can see: an OpenCode login, scoped to the model's own provider, and the CLI logins you tick for a nibblet. See below.) Each gets a base URL on the proxy and `NIBBLET_CREDPROXY_KEY`, which it sends where the harness would send an API key: its nibblet's id signed with the proxy's shared secret (`@nibblet/protocol/proxy-key`), so the proxy can tell whose a request is without asking, and an agent can't pass for another nibblet. A sub-agent gets its host's, since it runs in its host's container. The proxy checks the key, swaps in the real credential, and forwards:

| Proxy path                         | Upstream                                  | Injected                                                                                                               |
| ---------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `/anthropic/*`                     | `https://api.anthropic.com/*`             | `Authorization: Bearer <access>`, `anthropic-beta: oauth-2025-04-20` merged with any existing betas; drops `x-api-key` |
| `/openai/*`                        | `https://chatgpt.com/backend-api/codex/*` | `Authorization: Bearer <access>`, `chatgpt-account-id`                                                                 |
| `/deepseek/*`                      | `https://api.deepseek.com/anthropic/*`    | `x-api-key: <DEEPSEEK_API_KEY>`; drops `Authorization`                                                                 |
| `/openai-auth/oauth/token`         | answered locally                          | Dummy tokens, so a harness that tries to refresh its placeholder login gets a harmless answer                          |
| `GET /status`                      | answered locally (admin key)              | `CredentialStatus[]`                                                                                                   |
| `PUT /admin/credentials/:provider` | answered locally (admin key)              | The desktop app pushes keychain credentials here                                                                       |

Sources, per provider, are plugins: `file` (the host's `~/.claude/.credentials.json` or `~/.codex/auth.json`, bind-mounted read-write at `/creds/claude/.credentials.json` and `/creds/codex/auth.json`) and `keychain` (macOS: the desktop app reads `Claude Code-credentials` from the keychain and pushes it; refreshed tokens are pushed back through the desktop app's bridge). Refresh tokens rotate, so after refreshing the proxy writes the new pair back to its source, so the host's own CLI keeps working.

DeepSeek is an API key, not a login: `DEEPSEEK_API_KEY` in `docker/.env` (the installer asks for it), passed only to the proxy. There's nothing to refresh, and its status reads `env`.

Claude and ChatGPT can be API keys too, instead of subscriptions. The installer asks which when you set up Claude Code or Codex (or takes `NIBBLETS_ANTHROPIC_API_KEY` and `NIBBLETS_OPENAI_API_KEY`), and writes `CLAUDE_CREDENTIALS_SOURCE=api-key` with `NIBBLET_ANTHROPIC_API_KEY`, or `CODEX_AUTH_SOURCE=api-key` with `NIBBLET_OPENAI_API_KEY`, to `docker/.env`. Not `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`, since the host bridge loads that file and the host's own CLIs would pick those up. The harnesses don't change: Claude Code still sends the runner key, and Codex still has its placeholder ChatGPT login. The proxy's routes do:

| Proxy path     | Upstream (on an API key)      | Injected                                                                  |
| -------------- | ----------------------------- | ------------------------------------------------------------------------- |
| `/anthropic/*` | `https://api.anthropic.com/*` | `x-api-key: <key>`, no OAuth beta; drops `Authorization`                  |
| `/openai/*`    | `https://api.openai.com/v1/*` | `Authorization: Bearer <key>`; drops `x-api-key` and `chatgpt-account-id` |

Like DeepSeek's, these have nothing to refresh (a 401 goes straight back) and no subscription limit to note, their status reads `env`, and the desktop app keeps both lines when it rewrites `.env`.

### Budgets for API keys

A nibblet can have a monthly budget (`monthlyBudgetUsd`, set in its settings, which only offer it once the server has an API key) for what its usage on API keys costs: Claude or ChatGPT on a key, and DeepSeek. Subscriptions don't count. Months are calendar months in UTC. A sub-agent spends its host's budget, since its host's agent could read its key anyway.

- **Before each request on an API key,** the proxy checks whether the nibblet the key names still has budget (`BudgetGate` in `apps/credproxy/src/budgets.ts`). It counts what the server knows (`GET /credproxy/budget/:id`, with the admin key, asked at most every five seconds per nibblet) plus what it doesn't yet: requests still under way, and finished ones whose reports haven't landed. That way several requests at once can't each spend the same room. If the budget is spent, the proxy answers 402 with a `billing_error` saying so, in the harness's own API's shape, so the harness shows it. While the server can't be asked, the proxy uses what it last said for up to five minutes; after that, the request is refused rather than paid for. The bare shared secret isn't taken on these routes, since its spending would go to no one.
- **While a request runs,** it counts at a guess from its body's length, until its response says what it used. Then the proxy reads the usage off the response on its way through (the `message_start` and `message_delta` events of a Claude stream, `response.completed` of a Codex one, or a JSON body's `usage`) and reports it (`POST /credproxy/usage`). A stream the harness stops reading still counts its input, and the output it had streamed by then. A report the server doesn't take is kept, still counting, and tried again until it does. A response the API refused counts nothing.
- **The server prices it** with the table in `@nibblet/protocol`'s `budget.ts` and adds it to the nibblet's row in `spend`. Where a price is temporary or varies, the table has the higher one, a model it doesn't list costs as much as the provider's dearest, and OpenAI's uncached input is charged at its cache-write rate, so a budget runs out early rather than late. A request can still take spending a little past the budget, since it's only checked before each one starts.
- **A spent budget is waited out** like a usage limit: the turn the proxy refused goes back on the queue, and the nibblet waits (`limit_wait` with `reason: "budget"`) until the month turns. It carries on straight away if it no longer has to: when its budget is raised, or it's moved to a model or harness that doesn't spend it. Every five minutes the server checks for any other way out, such as the proxy going back to a subscription. OpenCode on the host's own login never waits, since it doesn't go through the proxy. While it waits, heartbeats and schedules don't pile up.

Refresh endpoints: Anthropic `POST https://platform.claude.com/v1/oauth/token` JSON `{grant_type:"refresh_token", refresh_token, client_id:"9d1c250a-e61b-44d9-88ed-5944d1962f5e"}`; OpenAI `POST https://auth.openai.com/oauth/token` `{grant_type:"refresh_token", refresh_token, client_id:"app_EMoamEEZ73f0CkXaXp7hrann"}`.

## Runner (`apps/runner`)

Started by the server with the `RunnerEnv` variables from `@nibblet/protocol`. It connects to `NIBBLET_SERVER_WS` with `Authorization: Bearer $NIBBLET_TOKEN`, waits for `configure`, opens the harness plugin for `config.harness`, and then runs `turn`s one at a time, streaming `item`s and ending each with `turn_end`. It keeps no durable state: the server sends the system prompt (instructions, relevant memories, a recap of the thread when the harness session is new) with every turn.

Harnesses get the `nibblet` MCP server (streamable HTTP at `NIBBLET_MCP_URL` with `Authorization: Bearer $NIBBLET_TOKEN`; the tools are below), plus whatever the guard serves through its gate.

### Inside the container: the guard and the agent

The agent runs whatever a model asks it to, so anything in its reach is in a prompt injection's reach. The container is split so its secrets aren't. The entry (`apps/runner/src/entry.ts`) starts as root, sets things up, and starts two processes under different users:

- **The guard** (uid 1100, `apps/runner/src/guard.ts`) holds the secrets. It runs OpenComputerUse (one Chromium on a headless Wayland display, with its profile in `/home/nibblet/.guard`, whose lock the guard clears before the browser starts, since one left by a container that didn't stop cleanly names a host that's gone and Chromium won't open the profile; and a view socket on port 7900 that the server proxies at `/api/nibblets/:id/computer`), the 1Password MCP server with its service account token, and the nibblet's own MCP servers with their headers and env. OpenComputerUse's own MCP endpoint listens on loopback only (`--listen-on 127.0.0.1`). All of them sit behind the gate on `127.0.0.1:7810`, which applies the nibblet's "ask me first" rules. The guard fetches its settings from the server's `/guard/:id/*` routes with `NIBBLET_GUARD_TOKEN`, and long-polls the server for approvals, so neither depends on anything the agent can touch.
- **The runner and the harness** (uid 1001, `nibblet`) only know the gate's address. They can't read the guard's environment, memory or home, and they never get the guard's token or the browser's view token.
- **Tailscale** (uid 1200), only for a nibblet on the user's tailnet. See below.

### The desktop: apps the agent and the user share

Besides the browser, a nibblet with the browser turned on has a desktop for its container's other apps (a terminal and a text editor in the image, and whatever the agent adds). It works like Infrawrench's app server: a launcher lists what's installed, either of them opens an app, and both see every app that's open, whoever opened it.

- **Who runs it:** a second OpenComputerUse (`apps/runner/src/desktop.ts`), started by the runner as the agent's user, with its MCP endpoint on `127.0.0.1:7801` and its view on port 7901. Not the guard's: every app OpenComputerUse starts runs as its user and inherits its environment, so an app the guard started could read the guard's tokens and the browser's profile. An app on the desktop can do what the agent can from its shell, and no more. The runner leaves its own `NIBBLET_*` variables out of the desktop's environment. It starts while the runner connects, and a harness waits for it before opening. If it doesn't come up there's no desktop, rather than one in each harness over stdio, as the browser falls back to.
- **Its token:** `NIBBLET_DESKTOP_TOKEN`, derived by the server from the host nibblet like the view token but apart from it, since the agent may know this one. It covers the MCP endpoint and the view.
- **What's installed:** `apps/runner/src/apps.ts` reads the XDG desktop entries (`~/.local/share/applications` first, then the system's), leaving out ones that are hidden, need a terminal, belong to one desktop, or aren't installed (`TryExec`), and Chromium, which has its own panel. Icons come from the icon themes and `pixmaps`, as `data:` URLs of up to 48 KB. The runner sends the list (`apps`) on connect and whenever a scan finds it changed; the server keeps the last one and passes changes to the UI as an `apps` live message. `nibblets.apps` answers with it and asks the runner to look again (`apps_scan`).
- **Opening apps:** the UI starts one at `POST /api/nibblets/:id/desktop/sessions`, which the server proxies to the view server with the token, like the browser's (`/desktop/*` beside `/computer/*`), and watches it on the same view protocol. The agent has the `apps` MCP server (`app_list`, and `app_launch`, which starts an app the same way, with files where its `Exec` line takes them, and returns its session id) and the desktop's own tools as `desktop`. Sessions are shared, so `list_sessions` there shows the user's apps too.
- **Sub-agents** use their host container's desktop (`NIBBLET_SUBAGENT`): they join its MCP endpoint, once it answers, rather than start one, and the UI shows the host's apps for them, going by the host's browser setting.
- **Adding apps:** the agent can't install system packages, so an app it adds goes under its home folder with a desktop entry in `~/.local/share/applications`. `APPIMAGE_EXTRACT_AND_RUN` is set, since there's no FUSE in the container.

Neither keeps any capability, and the server sets no-new-privileges, drops every capability the entry doesn't need, and limits processes. Before they start, the entry sets iptables rules: the cloud metadata range (169.254.0.0/16) is blocked, and on `nibblet-runners` only the server and the credential proxy are reachable, not other nibblets or the tunnel. The internet and `host.docker.internal` stay reachable: the first is the point, and OpenCode's local providers (such as Ollama) need the second. Downloads land in `/home/nibblet/Downloads`, which the agent can read.

### Sub-agents: beside their parent, in its container

A sub-agent works on its parent's files, with whatever the parent installed and alongside the servers it's running, so it runs in the parent's container (the top of the tree's, for a sub-agent's sub-agent) rather than its own. The server starts it with `docker exec` of `entry.ts subagent`, as root like the entry, which starts a second guard and runner pair under the same two users:

- **Its own browser:** its guard runs its own OpenComputerUse and Chromium, with a profile in `/home/nibblet/.guard/subagents/<id>`, so it gets its own window rather than the parent's. Its gate, browser and view listen on free ports the entry picks; the runner reports the view port in `ready`, and the server proxies the sub-agent's browser there.
- **Its own state:** the same working folder, but its harness keeps its home (sessions, config, its MCP servers and token) in `/home/nibblet/.subagents/<id>` (`HarnessContext.stateDir`), and its runner gets its own `TMPDIR`, for logins and task logs. Kimi doesn't trust the workdir for a sub-agent, since the `.kimi-code` there is the parent's.
- **Its lifetime:** stopping it signals the pid its entry leaves in `/run/nibblet-subagents`. It shares the container's CPU and memory limits, and goes when the container does: a restart asks the ones that were working to carry on once it's back, and a stop tells their parent's thread they stopped. Deleting it removes its state and profile.

1Password's `fill_login` never types into whatever the browser shows. It opens the login's own saved address (or a page the agent names on the same site), checks where it landed, and only then fills the username and password.

Harness plugins live in `packages/harness-*` and implement `HarnessPlugin` from `@nibblet/harness`, using `TurnWriter` to turn deltas into thread items.

### Tailscale: a nibblet on your tailnet

A nibblet can join the user's tailnet as a machine of its own, so the user can open what it runs from their other devices, and it can reach their machines. In its settings the user turns it on, and can set a machine name (made from its name otherwise) and the ports to share. Changing any of it restarts the container. Sub-agents are on the tailnet as their host container's machine.

- **Keys:** with a Tailscale OAuth client set up once in Settings (Auth Keys write scope, and the tags it owns), the server makes each nibblet a key when it signs in: single use, pre-approved, tagged, and good for an hour (`apps/server/src/tailnet-keys.ts`). The client's secret never leaves the server. A nibblet can still be given a key of its own instead, pasted into its settings.

- **Who runs it:** the entry starts `apps/runner/src/tailscale.ts` as a third user (uid 1200), neither the agent nor the guard. It fetches its settings from the server's `/guard/:id/tailscale` with the guard's token and starts `tailscaled` in userspace networking mode (no device, no capability). Only when the machine has to sign in does it ask `/guard/:id/tailscale/key` for a key (which may make one), and pass it to `tailscale up` in a file rather than on its command line. A machine that's already in just gets its name set. Then it reports how the machine is doing (`TailnetNode`) to the same route every time that changes. The server shows that in the settings, and tells the agent its address in the system prompt once it's running.
- **What the tailnet reaches:** in userspace mode, a connection from the tailnet is handed to 127.0.0.1 (or ::1) in the container by Tailscale's user. The entry's iptables rules let that user reach the shared ports on loopback, and the nameservers, and send replies on connections it didn't start (its proxy's, to the agent), and nothing else, so the gate, the browser and the runner's own servers stay out. Shared ports are below 20000 and never 7800, 7801, 7810, 7900, 7901 or 1055. If the rules can't be set, for IPv4 or for IPv6 where the container has it, Tailscale doesn't start, and the settings say why.
- **What the agent reaches:** the tailnet, through Tailscale's SOCKS5 and HTTP proxy on `127.0.0.1:1055`, which also resolves MagicDNS names. Nothing else changes for it: its traffic doesn't go through Tailscale unless it asks. It can't open the control socket (in a folder only Tailscale's user can), so it can't sign the machine out, `tailscale serve` anything, or read the key.
- **State:** the machine's keys live on a volume of their own (`nibblet-tailscale-<id>` at `/var/lib/nibblet-tailscale`), not the home volume, where the agent could swap in state of its own. It isn't snapshotted, and it's deleted with the nibblet. Once joined, the machine stays signed in across restarts, so a one-off key is enough. A different key, or OAuth client, signs out and joins again. Taking a nibblet off the tailnet, or deleting it, signs its machine out and empties the volume: its own container does it when it restarts, and while it's asleep a short-lived one (`entry.ts tailscale-leave`, with only that volume) does.

### Background tasks and terminals

- **Background tasks:** the runner serves a local `tasks` MCP server (`apps/runner/src/tasks.ts`), as it does `files`: `task_start`, `task_list`, `task_output` and `task_stop`. Each task is `bash -lc <command>` in its own process group, as the agent's user, with its output in a log under `/tmp`. It outlives the turn that started it, but not the container. A task is running for as long as anything in its process group is, so a script that starts a server with `&` and returns still shows (and stops) as running. When the container stops, tasks get SIGTERM and 8 seconds to finish (time for a game server to save) before SIGKILL; the server stops runner containers with `docker stop -t 12` for that. Logs are cut back to their last megabyte once they pass 16 MB. The runner sends the list to the server (a `tasks` message) whenever it changes and on every connect; the server passes it to the UI as a `tasks` live message, and `nibblets.tasks` answers the first ask. The user stops one with `nibblets.stopTask`, which the server passes on as `task_stop`.
- **Terminals:** the UI opens a WebSocket at `/api/nibblets/:id/terminal?cols=&rows=[&task=]`, with a ticket like the live socket. The server carries it over the runner's socket (`terminal_open`, `terminal_input`, `terminal_resize`, `terminal_ack` and `terminal_close` down; `terminal_output` and `terminal_exit` up), so there's no new port in the container. The runner starts a login shell, or `tail -F` of a task's log, in a pseudo-terminal through `terminal-pty.py`, since node-pty would need a compiler the image doesn't have. It runs as the agent's user, so it reaches what the agent reaches and nothing of the guard's. The browser acknowledges output once xterm.js has drawn it, and a terminal stops reading when more than 512K characters are unacknowledged, so a flood (`yes`, a huge `cat`) can't pile up in the runner, the server, or in front of a turn's messages on the same socket. The terminal ends when its shell exits, even if a background job still holds it open. A runner can only answer terminals opened on it, and terminal output is never kept for a reconnect: when the socket drops, the runner hangs up every shell.

### OpenCode

OpenCode nibblets use the host's own OpenCode account, not the credential proxy. The host bridge reports whether OpenCode is set up (`GET /harness/opencode`: the CLI, OpenCode.app, or a config or login in its XDG directories) and hands over the config and `auth.json` (`GET /harness/opencode/login`, bridge token only).

- **The model picker:** `harnesses.models({ harness: "opencode" })` lists whatever OpenCode offers for that login. The server runs `apps/runner/src/opencode-models.ts` in a throwaway runner container with the login on stdin, so the list is exactly what a nibblet will see, and caches it for a minute. The host doesn't need the CLI.
- **On each configure:** the server fetches the login fresh, keeps only the entry for the nibblet's model's provider, and sends it only over the runner socket. The runner writes the config into the container, and the login to `/tmp/nibblet-secrets/opencode-auth.json`, with OpenCode's `auth.json` a link to it, so it never lands in the home folder or its snapshots.
- **What changes in the container:** the host config's `mcp` section is dropped, because the nibblet brings its own servers. Provider URLs on the host's `localhost` or `127.0.0.1` are pointed at `host.docker.internal`, so a local Ollama still resolves.
- **Not written back:** a provider whose OAuth token refreshes inside the container doesn't write it back to the host.
- **Without a bridge or a login:** OpenCode falls back to Anthropic and OpenAI through the credential proxy.

### DeepSeek

DeepSeek nibblets are the Claude harness on DeepSeek's Anthropic-compatible API. `@nibblet/harness-deepseek` is a few lines on `claudeCodeHarness` from `@nibblet/harness-claude`, the same Claude Agent SDK loop and mapper, with the base URL set to the proxy's `/deepseek` route instead of `/anthropic`.

- **The CLI:** it runs Claude Code, so it has no CLI of its own (`cliOf: "claude"`). The updater lists and installs Claude Code once, under Claude, and DeepSeek nibblets use that one too.
- **Models:** V4.1 Flash (`deepseek-flash`, which DeepSeek keeps on its newest Flash) and V4 Pro (`deepseek-v4-pro`), both with DeepSeek's effort levels (`low`, `high`, `max`). Effort is only sent for a level the model declares, so `medium` is left to DeepSeek. Only Flash takes images; V4 Pro gets their paths. Claude Code's own background work runs on Flash (`ANTHROPIC_DEFAULT_HAIKU_MODEL`).
- **Offered:** once the proxy reports a key, like Claude and Codex once their subscriptions are signed in. Its Settings row only shows once a key is set.

### Kimi Code

Kimi nibblets use the host's own Kimi Code CLI login, like OpenCode ones. The host bridge reports whether Kimi Code is set up (`GET /harness/kimi`: the `kimi` CLI on PATH, or a `config.toml` or token under `$KIMI_CODE_HOME`) and hands over the config and the OAuth token (`GET /harness/kimi/login`, bridge token only).

- **On each configure:** the server fetches the login fresh and sends it only over the runner socket. The runner writes the config into `<workdir>/.kimi-code/config.toml`, and the token to `/tmp/nibblet-secrets/kimi-code.json`, with `credentials/kimi-code.json` a link to it, so it never lands in the home volume or its snapshots.
- **What the CLI is asked for:** one process per turn, `kimi -p <prompt> --output-format stream-json`, which never asks for approval, so nothing waits on a person who isn't in the container. The stream is OpenAI chat shaped, which `KimiMapper` turns into thread items; sessions live on disk and the next turn resumes with `--session`.
- **What changes in the container:** the nibblet's own MCP servers go in `<workdir>/.kimi-code/mcp.json`. Because that path is also where Kimi looks for a project's servers, the turn runs with `KIMI_CODE_TRUST_WORKSPACE=1`, the same trust the other harnesses give their workdir.
- **Without a bridge or a login:** the harness says so rather than guessing at credentials. Kimi Code has no credential proxy to fall back to.
- **Effort:** OpenCode has no effort setting, so its models carry none and the effort menu is hidden.

## Bank: cards and wallets

A nibblet can be given money to spend, as virtual cards or as crypto wallets that work like them. Where the money comes from is a bank plugin (`packages/bank-*`) implementing `BankPlugin` from `@nibblet/bank`: it issues a card with a lifetime limit, gives its details again (`reveal`), reports what's been spent on it (`inspect`), and closes it (`close`). Each plugin's factory describes its own settings form (`fields`: labels, hints, secrets, choices, keys the form can make, and fields that can't change while cards are open), so Settings → Bank sets any of them up without the web app knowing one bank from another. Saving checks the settings with the provider (`check`), keeps them in the `settings` table (`banks`, secrets never sent back), and loads the plugin without a restart (`apps/server/src/banks.ts`, which lists the plugins). There can be several banks on one plugin (two Slash accounts, or a signet and a mainnet treasury), each with its own id, settings and name; one per plugin can go without a name. The first bank on a plugin gets the plugin's own id (`slash`) and later ones one from their name (`slash-travel`), and a card keeps its bank's id, so renaming a bank never strands its cards. A plugin with no saved bank under its own id also gets one from the server's environment, whose variables are named like its fields. A plugin holds its provider's credentials, which never leave the server. Settings shows each bank, its balance, where to top a treasury up (`fundAt`), and any whose settings are wrong. A bank can't be removed, or have its locked fields changed, while it has cards that aren't closed.

- **Limits:** the person sets each nibblet's `spendingLimits`, one per asset (`USD`, `BTC`, `ETH`), per day, week or month (UTC) or in total. A nibblet has none to begin with, so it can't have a card until it's given one, and it can't change its own. Every card counts against its period for its whole limit while it's open, since it could all still be spent, and for what was spent once it's closed. One request or kill at a time per nibblet, so two at once can't both fit the same budget.
- **The card file:** `card_request` asks the plugin for a card, stores its record (`cards`: never the number or key), and sends its details over the runner socket (`card_put`). The runner writes them to `$TMPDIR/nibblet-cards/<id>.json`, `0600` in a `0700` folder, as the agent's user, and answers `card_done` with the path, which is all the tool returns. So a card's number reaches the model only if it reads the file, and never the thread, the database or a snapshot. A card that can't be written is closed again. The folder goes with the container; when a runner reconnects, the server asks the plugins for its open cards again and rewrites them.
- **Card states:** a card's row goes in as `pending` before the plugin is asked for it, so one the provider made before something failed (a timeout after it was sent) is never lost: every minute the server asks the plugin to `find` pending cards it isn't still making, closes any that were made, and forgets ones that haven't shown up in an hour. A plugin throws a `BankError` only for a refusal, where nothing was made; its message is the only kind passed on, since other errors can carry credentials (an RPC URL with its key), so they're logged on the server instead.
- **Closing:** `card_kill` (the nibblet, its own cards), Kill in the UI (the person, any), and deleting a nibblet close cards at the provider and delete their files. A card the provider can't settle yet (a wallet whose funding isn't seen, so there's nothing to sweep) stays `closing`, counting in full, and the server tries again every minute; after a day it's recorded as closed with a warning in the log. A nibblet with a card that can't be closed isn't deleted, so the card's record (and a wallet's id, from which its key comes) isn't lost. Every minute the server also checks open cards with their providers: it records what's been spent, notices cards the provider closed, and closes single-use cards that have been used where the provider doesn't do that itself.
- **Slash** (`packages/bank-slash`, `USD`): virtual cards on the person's Slash account, set up with `SLASH_API_KEY` (with the cards.view and cards.manage permissions), plus `SLASH_ACCOUNT_ID` for the account cards are made under and whose balance Settings shows (Slash picks the first commercial account otherwise). Single-use cards are Slash's own `isSingleUse`, which Slash closes after the first authorisation; both kinds carry a `collective` (never resetting) utilisation limit of the card's limit, so Slash declines anything over it. Each card is tagged with its id in `userData`, which is how `find` recognises it.
- **Stripe** (`packages/bank-stripe`, `USD`, `EUR` or `GBP`): virtual cards from Stripe Issuing, set up with `STRIPE_API_KEY` (a secret key, or a restricted one that can write Issuing cards and read cardholders, authorizations, transactions and balances) and `STRIPE_CARDHOLDER_ID` (the `ich_` cardholder cards are made for, whose billing address goes in each card's file), plus `STRIPE_CURRENCY` for an Issuing balance that isn't in US dollars, and `STRIPE_WEBHOOK_SECRET` to approve each purchase (below). Each card carries an `all_time` spending limit of the card's limit, so Stripe declines anything over it. Stripe has no single-use cards, so a single-use one counts as used once anything but a zero-amount check has gone through it, and the server cancels it. What's spent is captures net of refunds plus authorisations not yet captured. A card whose number Stripe won't hand over is cancelled again as soon as it's made. Taking live card numbers over the API puts the server, and wherever a card's file is read, in scope for PCI DSS: Stripe's own advice is to keep them to its Dashboard and Issuing Elements. Each card is tagged with its id in `metadata`, which is how `find` recognises it.
- **Approving each purchase:** a plugin whose provider can ask before each purchase says where its form is (`purchaseHook` on the factory), and a bank set up to answer has `purchases` (Stripe's real-time authorizations, once `STRIPE_WEBHOOK_SECRET` is set). The provider posts to `/bank/<plugin>/purchases`, which nobody signs in to: each bank on that plugin checks the request's signature (`read`), and the one that signed it says which card it's for. Banks on one Stripe account share its one webhook and so its secret, so the card is looked for at every bank that signed the request. The server approves only if that card is open, the purchase is in its asset and fits what's left of its limit, counting what it approved since shortly before the card was last checked with the provider (which may not have shown those yet), and a single-use card makes only one purchase, though that one can ask for more on the same authorisation (a hotel stay running on) and zero-amount checks don't count. The provider asks about every card on the account, so a purchase on a card that isn't a nibblet's (one without the server's tag, Stripe's `metadata`) is approved, leaving it to the provider's own rules, while one tagged as a nibblet's that this server doesn't know is declined. Anything it can't read or check is declined, and so is everything when the server can't be reached, as long as the person has set the provider to decline when it gets no answer (Stripe's timeout setting, in its Dashboard). The provider reaches the server at its public address (below); Settings → Bank shows the address to give the provider, and warns that a quick tunnel's changes whenever it starts.
- **Verifying a payment:** when a checkout asks to verify the payment (3-D Secure: a code sent by text or email, or the bank's own page), the nibblet calls `card_verify` and leaves the page alone. That's an approval in its thread, which notifies the person; they open its browser, do the verification there themselves, so the code never reaches the model, and press Done or Couldn't. Meanwhile the nibblet's status says what it's waiting for, and goes back to what it was once they've answered. A tool call that waits too long is dropped by some harnesses (Codex gives up after a minute), so `card_verify` returns after about 40 seconds if they haven't answered, and the nibblet calls `card_verify_wait` to wait again. This works for any bank's cards.
- **Wallets:** a crypto plugin funds a fresh wallet per card from its treasury with exactly the card's limit, so the limit holds on chain. The wallet's key is derived from the treasury's secret and the card's id (`deriveWalletKey`), so none is stored, and killing the card sweeps what's left back to the treasury.
- **Bitcoin** (`packages/bank-bitcoin`, `BTC`): `BITCOIN_TREASURY_KEY` (hex or WIF) and `BITCOIN_NETWORK` (`mainnet`, `testnet`, `signet` or `regtest`, with no default, so a test key never lands on mainnet by accident), plus `BITCOIN_ESPLORA_URL` (mempool.space's API by default; needed for regtest) and `BITCOIN_FEE_RATE` (sat/vB, instead of Esplora's estimate). The treasury and every card wallet are native segwit (P2WPKH), signed with `@scure/btc-signer`. A card needs at least 5,000 sats.
- **Ethereum** (`packages/bank-ethereum`, `ETH`): `ETHEREUM_TREASURY_KEY` and `ETHEREUM_RPC_URL`, plus `ETHEREUM_CHAIN_ID` (checked against the RPC before anything is sent) and `ETHEREUM_ASSET` for another EVM chain's coin (`POL`, say). Plain transfers, signed with `viem`. Gas comes out of the card's own balance. The sweep pays exactly 21,000 gas at the current price, so chains that also charge an L1 data fee (Base, Optimism and other OP Stack chains) aren't supported yet: their sweeps would fail, and killed cards would stay `closing`.
- **What a wallet can't do:** a nibblet holds its wallet's key, so it can spend all of the wallet's limit, and nothing more, the moment it has it; network fees, the sweep's included, count as spent. Killing a card sweeps what's left, but a nibblet that copied the key before could race the sweep for it, so treat a crypto card's limit as given away.

## API

The typed contract is `contract` in `packages/protocol/src/contract.ts`. Calls are `POST /api/rpc/<dotted.path>`. Live updates are a WebSocket at `/api/live` pushing `LiveMessage`s. Browsers authenticate with `Authorization: Bearer <token>`; WebSockets take `?ticket=` from `POST /api/ticket`, which lasts 30 seconds, so long-lived tokens never go in URLs.

First run prints, and the desktop app opens, a pairing link `http(s)://host/#pair=<code>`. The UI exchanges the code at `POST /api/pair` for a long-lived token.

## Across machines: Nibblets Connect (`apps/connect`)

Each machine runs its own server. Like T3 Connect, a central service (a Cloudflare Worker with D1, signed in with Clerk) lists every server on an account, without being in the data path:

- A server links with a code approved on the central site, then sends a heartbeat every 30 seconds with its routes: local network (`NIBBLET_LAN_URLS`), Tailscale (`tailscale serve` through the host bridge), and a Cloudflare tunnel (a managed one when the central service has a zone, a quick one otherwise).
- Approving a link shows where the server asked from. If that's a different network from yours, you have to tick that you started it yourself, so a code sent by someone else can't quietly add their server to your account. Every device you're signed in on is told when a server is linked.
- The central UI (the web app built with `build:central`) tries each server's routes in that order with a `/healthz` probe, and talks to the first that answers with a five-minute ES256 token from the central service. Servers verify those tokens against its JWKS.
- The desktop app asks on first run whether to run a server on this computer. If not, it only shows the central UI.
- "Pair a device" still signs a device in to one server directly, on the same network.
- **Public address** (`apps/server/src/public-address.ts`, the `publicAddress` RPCs): how the server is reached from the internet, for anything that needs to be told, such as a card provider asking about purchases (above) or a pairing link. It's the person's own reverse proxy's address when they've given one under Remote access (the `publicProxy` setting), or else the tunnel's while it's up, or else none; pairing links fall back to `NIBBLET_PUBLIC_URL`.

See `apps/connect/README.md` for deploying it.

## Host tools (`packages/host-mcp`)

The host bridge runs on the host, in the desktop app (127.0.0.1:8789) or as `node packages/host-mcp/src/cli.ts --port 8789 --token <t> [--host 172.17.0.1]` on servers without it. The server reaches it at `HOST_MCP_URL` with `HOST_MCP_TOKEN`; empty turns it off. Nothing reaches a nibblet unless ticked for it.

- **Host MCP servers**: read in Claude's `mcpServers` format from `~/.nibblet/host-mcp.json`, then Claude Code's `~/.claude.json`, then Claude Desktop's config, with the first definition of a name winning. Each server is started on first use and served at `/mcp/<name>`; `GET /servers` lists them. A nibblet's `hostTools` names the ones it may use. Its runner registers each as `host_<name>` at the server's `/hostmcp/<name>`, which checks the nibblet's token and that list before forwarding.
- **CLI logins**: `CliPlugin`s (`gh` and `ssh` so far) detect whether a CLI is installed and signed in (`GET /clis`) and turn its login into environment variables (`GET /clis/:id/credential`). For each CLI in a nibblet's `cliCredentials`, the server fetches a fresh credential on every configure and sends it only over the runner socket. The runner puts it in the harness's environment and runs the CLI's setup (`gh auth setup-git`). It is never stored, logged, or returned by the API.
- **SSH keys**: the `ssh` plugin shares the host's SSH agent, never a key. It's offered when `ssh-add -l` lists keys. For a nibblet that has it ticked, the server bind-mounts `HOST_SSH_AUTH_SOCK` (`/run/host-services/ssh-auth.sock` on Docker Desktop and OrbStack, the host's `$SSH_AUTH_SOCK` on Linux) at `/run/nibblet/ssh-agent.sock`. Because it's a mount, ticking or unticking it restarts the container. On Linux the socket is usually `0600`, owned by the host user, so the container's `nibblet` user (uid 1001) can't open it unless the uids match.
- **A nibblet's own MCP servers** (`mcpServers`): remote URLs, or commands run inside its container by the guard. Header and env values are secrets: the API returns them as `••••`, an update that sends `••••` back keeps the stored value, and only the guard receives them.
- **Host tool approvals**: `/hostmcp/<name>` reads each request before forwarding it, and refuses batches and anything it can't read, so an "ask me first" host tool can't be called without asking.

Shared memories are written to the system prompt only when they're the nibblet's own. Other nibblets' shared notes come back from `memory_search` marked as information, not instructions.
