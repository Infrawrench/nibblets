# Architecture

Nibblets are self-hosted, always-on agents, each drawn as a hamster you can dress up. A nibblet is a thread: it runs in a machine of its own (a Docker container, or a virtual machine on the host; see [Machines](#machines-containers-and-virtual-machines)) on one of its harnesses (Claude Agent SDK, Codex, OpenCode, Kimi Code), wakes on a heartbeat and on schedules, keeps its memory outside the container in Postgres with pgvector, and can spawn sub-agents, which are child nibblets that run in their parent's container.

## Processes

Everything runs in Docker on two networks. `nibblet` has the database, the server and the credential proxy. `nibblet-runners` has the server, the credential proxy and the nibblets' containers, so a nibblet can't reach the database.

| Service        | Image                          | Address on the network | What it does                                                                                                                       |
| -------------- | ------------------------------ | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `server`       | `nibblet/server`               | `server:8420`          | API, web UI, live WebSocket, runner WebSocket, nibblet tools over MCP, scheduler, heartbeats, Docker orchestration, tunnels        |
| `db`           | `pgvector/pgvector:0.8.7-pg18` | `db:5432`              | All durable state: nibblets, thread items, schedules, memories (with embeddings), peers, sign-ins                                  |
| `credproxy`    | `nibblet/credproxy`            | `credproxy:8787`       | Holds the host's Claude and ChatGPT subscription credentials, refreshes them, and injects them into harness traffic                |
| `tunnel`       | `cloudflare/cloudflared`       | none                   | Started by the server when a tunnel is configured                                                                                  |
| `nibblet-<id>` | `nibblet/runner`               | `nibblet-<id>`         | One per running nibblet in a container: the runner, its harness, OpenComputerUse with Chromium, and the desktop for its other apps |

The server is published on the host at `127.0.0.1:8420`, and the credential proxy at `127.0.0.1:8787`, for the host bridge to reach on behalf of nibblets in virtual machines. The server mounts the Docker socket to manage the tunnel and runner containers. Docker is always needed: it runs the stack, whatever the nibblets run in.

## Credentials (`apps/credproxy`)

Runner containers never see a Claude or ChatGPT subscription token. (What they can see: an OpenCode login, scoped to the model's own provider, and the CLI logins you tick for a nibblet. See below.) Each gets a base URL on the proxy and `NIBBLET_CREDPROXY_KEY`, which it sends where the harness would send an API key: its nibblet's id signed with the proxy's shared secret (`@nibblets/protocol/proxy-key`), so the proxy can tell whose a request is without asking, and an agent can't pass for another nibblet. A sub-agent gets its host's, since it runs in its host's container. The proxy checks the key, swaps in the real credential, and forwards:

| Proxy path                         | Upstream                                  | Injected                                                                                                                                                                 |
| ---------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/anthropic/*`                     | `https://api.anthropic.com/*`             | `Authorization: Bearer <access>`, `anthropic-beta: oauth-2025-04-20` merged with any existing betas; drops `x-api-key`; Claude Code reads as the interactive CLI (below) |
| `/openai/*`                        | `https://chatgpt.com/backend-api/codex/*` | `Authorization: Bearer <access>`, `chatgpt-account-id`                                                                                                                   |
| `/deepseek/*`                      | `https://api.deepseek.com/anthropic/*`    | `x-api-key: <DEEPSEEK_API_KEY>`; drops `Authorization`                                                                                                                   |
| `/openai-auth/oauth/token`         | answered locally                          | Dummy tokens, so a harness that tries to refresh its placeholder login gets a harmless answer                                                                            |
| `GET /status`                      | answered locally (admin key)              | `CredentialStatus[]`                                                                                                                                                     |
| `PUT /admin/credentials/:provider` | answered locally (admin key)              | The desktop app pushes keychain credentials here                                                                                                                         |

On a subscription, Claude Code's requests are made to read as its interactive CLI's, since subscriptions meter the Agent SDK's faster for the same tokens: its `User-Agent` entrypoint becomes `(external, cli)`, `x-app` is `cli`, and the billing line it puts first in `system` says `cc_entrypoint=cli`. Its version stays its own. Other harnesses' requests, and any on an API key, go as they came.

Sources, per provider, are plugins: `file` (the host's `~/.claude/.credentials.json` or `~/.codex/auth.json`, bind-mounted read-write at `/creds/claude/.credentials.json` and `/creds/codex/auth.json`) and `keychain` (macOS: the desktop app reads `Claude Code-credentials` from the keychain and pushes it; refreshed tokens are pushed back through the desktop app's bridge). Refresh tokens rotate, so after refreshing the proxy writes the new pair back to its source, so the host's own CLI keeps working.

DeepSeek is an API key, not a login: `DEEPSEEK_API_KEY` in `docker/.env` (the installer asks for it), passed only to the proxy. There's nothing to refresh, and its status reads `env`.

Claude and ChatGPT can be API keys too, instead of subscriptions. The installer asks which when you set up Claude Code or Codex (or takes `NIBBLETS_ANTHROPIC_API_KEY` and `NIBBLETS_OPENAI_API_KEY`), and writes `CLAUDE_CREDENTIALS_SOURCE=api-key` with `NIBBLET_ANTHROPIC_API_KEY`, or `CODEX_AUTH_SOURCE=api-key` with `NIBBLET_OPENAI_API_KEY`, to `docker/.env`. Not `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`, since the host bridge loads that file and the host's own CLIs would pick those up. The harnesses don't change: Claude Code still sends the runner key, and Codex still has its placeholder ChatGPT login. The proxy's routes do:

| Proxy path     | Upstream (on an API key)      | Injected                                                                  |
| -------------- | ----------------------------- | ------------------------------------------------------------------------- |
| `/anthropic/*` | `https://api.anthropic.com/*` | `x-api-key: <key>`, no OAuth beta; drops `Authorization`                  |
| `/openai/*`    | `https://api.openai.com/v1/*` | `Authorization: Bearer <key>`; drops `x-api-key` and `chatgpt-account-id` |

Like DeepSeek's, these have nothing to refresh (a 401 goes straight back) and no subscription limit to note, their status reads `env`, and the desktop app keeps both lines when it rewrites `.env`.

### Budgets for API keys

A nibblet can have a monthly budget (`monthlyBudgetUsd`, set in its settings, which only offer it once the server has an API key) for what its usage on API keys costs: Claude or ChatGPT on a key, and DeepSeek. Subscriptions don't count. Months are calendar months in UTC. A sub-agent spends its host's budget, since its host's agent could read its key anyway.

- **Before each request on an API key,** the proxy checks whether the nibblet the key names still has budget (`BudgetGate` in `apps/credproxy/src/budgets.ts`). It counts what the server knows (`GET /credproxy/budget/:id`, with the admin key, asked at most every five seconds per nibblet) plus what it doesn't yet: requests still under way, and finished ones whose reports haven't landed. That way several requests at once can't each spend the same room. If the budget is spent, the proxy answers 402 with a `billing_error` saying so, in the harness's own API's shape, so the harness shows it. While the server can't be asked, the proxy uses what it last said for up to five minutes; after that, the request is refused rather than paid for. The bare shared secret isn't taken on these routes, since its spending would go to no one.
- **While a request runs,** it counts at a guess from its body's length, until its response says what it used. Then the proxy reads the usage off the response on its way through (the `message_start` and `message_delta` events of a Claude stream, `response.completed` of a Codex one, or a JSON body's `usage`) and reports it (`POST /credproxy/usage`). A stream the harness stops reading still counts its input, and the output it had streamed by then. A report the server doesn't take is kept, still counting, and tried again until it does. A response the API refused counts nothing.
- **The server prices it** with the table in `@nibblets/protocol`'s `budget.ts` and adds it to the nibblet's row in `spend`. Where a price is temporary or varies, the table has the higher one, a model it doesn't list costs as much as the provider's dearest, and OpenAI's uncached input is charged at its cache-write rate, so a budget runs out early rather than late. A request can still take spending a little past the budget, since it's only checked before each one starts.
- **A spent budget is waited out** like a usage limit: the turn the proxy refused goes back on the queue, and the nibblet waits (`limit_wait` with `reason: "budget"`) until the month turns. It carries on straight away if it no longer has to: when its budget is raised, or it's moved to a model or harness that doesn't spend it. Every five minutes the server checks for any other way out, such as the proxy going back to a subscription. OpenCode on the host's own login never waits, since it doesn't go through the proxy. While it waits, heartbeats and schedules don't pile up.

Refresh endpoints: Anthropic `POST https://platform.claude.com/v1/oauth/token` JSON `{grant_type:"refresh_token", refresh_token, client_id:"9d1c250a-e61b-44d9-88ed-5944d1962f5e"}`; OpenAI `POST https://auth.openai.com/oauth/token` `{grant_type:"refresh_token", refresh_token, client_id:"app_EMoamEEZ73f0CkXaXp7hrann"}`.

## Runner (`apps/runner`)

Started by the server with the `RunnerEnv` variables from `@nibblets/protocol`. It connects to `NIBBLET_SERVER_WS` with `Authorization: Bearer $NIBBLET_TOKEN`, waits for `configure`, opens the harness plugin for `config.harness`, and then runs `turn`s one at a time, streaming `item`s and ending each with `turn_end`. It keeps no durable state: the server sends the system prompt (instructions, relevant memories, a recap of the thread when the harness session is new) with every turn.

Harnesses get the `nibblet` MCP server (streamable HTTP at `NIBBLET_MCP_URL` with `Authorization: Bearer $NIBBLET_TOKEN`; the tools are below), plus whatever the guard serves through its gate.

### Inside the container: the guard and the agent

The agent runs whatever a model asks it to, so anything in its reach is in a prompt injection's reach. The container is split so its secrets aren't. The entry (`apps/runner/src/entry.ts`) starts as root, sets things up, and starts two processes under different users:

- **The guard** (uid 1100, `apps/runner/src/guard.ts`) holds the secrets. It runs OpenComputerUse (one Chromium on a headless Wayland display, with its profile in `/home/nibblet/.guard`, whose lock the guard clears before the browser starts, since one left by a container that didn't stop cleanly names a host that's gone and Chromium won't open the profile; and a view socket on port 7900 that the server proxies at `/api/nibblets/:id/computer`), the 1Password MCP server with its service account token, the nibblet's own MCP servers with their headers and env, and its app links' servers with their credentials (see [App links](#app-links-identities-in-other-apps)). OpenComputerUse's own MCP endpoint listens on loopback only (`--listen-on 127.0.0.1`). All of them sit behind the gate on `127.0.0.1:7810`, which applies the nibblet's "ask me first" rules. The guard fetches its settings from the server's `/guard/:id/*` routes with `NIBBLET_GUARD_TOKEN`, and long-polls the server for approvals, so neither depends on anything the agent can touch.
- **The runner and the harness** (uid 1001, `nibblet`) only know the gate's address. They can't read the guard's environment, memory or home, and they never get the guard's token or the browser's view token.
- **Tailscale** (uid 1200), only for a nibblet on the user's tailnet. See below.

### The desktop: apps the agent and the user share

Besides the browser, a nibblet with the browser turned on has a desktop for its container's other apps (a terminal and a text editor in the image, and whatever the agent adds). It works like Infrawrench's app server: a launcher lists what's installed, either of them opens an app, and both see every app that's open, whoever opened it.

- **Who runs it:** a second OpenComputerUse (`apps/runner/src/desktop.ts`), started by the runner as the agent's user, with its MCP endpoint on `127.0.0.1:7801` and its view on port 7901. Not the guard's: every app OpenComputerUse starts runs as its user and inherits its environment, so an app the guard started could read the guard's tokens and the browser's profile. An app on the desktop can do what the agent can from its shell, and no more. The runner leaves its own `NIBBLET_*` variables out of the desktop's environment. It starts while the runner connects, and a harness waits for it before opening. If it doesn't come up there's no desktop, rather than one in each harness over stdio, as the browser falls back to.
- **Its token:** `NIBBLET_DESKTOP_TOKEN`, derived by the server from the host nibblet like the view token but apart from it, since the agent may know this one. It covers the MCP endpoint and the view.
- **What's installed:** `apps/runner/src/apps.ts` reads the XDG desktop entries (`~/.local/share/applications` first, then the system's), leaving out ones that are hidden, need a terminal, belong to one desktop, or aren't installed (`TryExec`), and Chromium, which has its own panel. Icons come from the icon themes and `pixmaps`, as `data:` URLs of up to 48 KB. The runner sends the list (`apps`) on connect and whenever a scan finds it changed; the server keeps the last one and passes changes to the UI as an `apps` live message. `nibblets.apps` answers with it and asks the runner to look again (`apps_scan`).
- **Opening apps:** the UI starts one at `POST /api/nibblets/:id/desktop/sessions`, which the server proxies to the view server with the token, like the browser's (`/desktop/*` beside `/computer/*`), and watches it on the same view protocol. The agent has the `apps` MCP server (`app_list`, and `app_launch`, which starts an app the same way, with files where its `Exec` line takes them, and returns its session id) and the desktop's own tools as `desktop`. Sessions are shared, so `list_sessions` there shows the user's apps too.
- **Sub-agents** use their host container's desktop (`NIBBLET_SUBAGENT`): they join its MCP endpoint, once it answers, rather than start one, and the UI shows the host's apps for them, going by the host's browser setting.
- **Adding apps:** the agent can't install system packages, so an app it adds goes under its home folder with a desktop entry in `~/.local/share/applications`. `APPIMAGE_EXTRACT_AND_RUN` is set, since there's no FUSE in the container.

Neither keeps any capability, and the server sets no-new-privileges, drops every capability the entry doesn't need, and limits processes. Before they start, the entry sets iptables rules: the cloud metadata range (169.254.0.0/16) is blocked, and on `nibblet-runners` only the server and the credential proxy are reachable, not other nibblets or the tunnel. The internet and `host.docker.internal` stay reachable: the first is the point, and OpenCode's local providers (such as Ollama) need the second. Downloads land in `/home/nibblet/Downloads`, which the agent can read.

### Sub-agents: beside their parent, in its container

A sub-agent works on its parent's files, with whatever the parent installed and alongside the servers it's running, so it runs in the parent's container (the top of the tree's, for a sub-agent's sub-agent) rather than its own. The server starts it with `docker exec` of `entry.ts subagent`, as root like the entry, which starts a second guard and runner pair under the same two users:

- **Its own browser:** its guard runs its own OpenComputerUse and Chromium, with a profile in `/home/nibblet/.guard/subagents/<id>`, so it gets its own window rather than the parent's. Its gate, browser and view listen on free ports the entry picks; the runner reports the view port in `ready`, and the server proxies the sub-agent's browser there.
- **Its own state:** the same working folder, but its harness keeps its home (sessions, config, its MCP servers and token) in `/home/nibblet/.subagents/<id>` (`HarnessContext.stateDir`), and its runner gets its own `TMPDIR`, for logins and task logs. Kimi doesn't trust the workdir for a sub-agent, since the `.kimi-code` there is the parent's.
- **Its lifetime:** stopping it signals the pid its entry leaves in `/run/nibblet-subagents`. It shares the container's CPU and memory limits, and goes when the container does: a restart asks the ones that were working to carry on once it's back, and a stop tells their parent's thread they stopped. Deleting it removes its state and profile.

1Password's `fill_login` never types into whatever the browser shows. It opens the login's own saved address (or a page the agent names on the same site), checks where it landed, and only then fills the username and password.

Harness plugins live in `packages/harness-*` and implement `HarnessPlugin` from `@nibblets/harness`, using `TurnWriter` to turn deltas into thread items.

### Tailscale: a nibblet on your tailnet

A nibblet can join the user's tailnet as a machine of its own, so the user can open what it runs from their other devices, and it can reach their machines. In its settings the user turns it on, and can set a machine name (made from its name otherwise) and the ports to share. Changing any of it restarts the container. Sub-agents are on the tailnet as their host container's machine.

- **Keys:** with a Tailscale OAuth client set up once in Settings (Auth Keys write scope, and the tags it owns), the server makes each nibblet a key when it signs in: single use, pre-approved, tagged, and good for an hour (`apps/server/src/tailnet-keys.ts`). The client's secret never leaves the server. A nibblet can still be given a key of its own instead, pasted into its settings.

- **Who runs it:** the entry starts `apps/runner/src/tailscale.ts` as a third user (uid 1200), neither the agent nor the guard. It fetches its settings from the server's `/guard/:id/tailscale` with the guard's token and starts `tailscaled` in userspace networking mode (no device, no capability). Only when the machine has to sign in does it ask `/guard/:id/tailscale/key` for a key (which may make one), and pass it to `tailscale up` in a file rather than on its command line. A machine that's already in just gets its name set. Then it reports how the machine is doing (`TailnetNode`) to the same route every time that changes. The server shows that in the settings, and tells the agent its address in the system prompt once it's running.
- **What the tailnet reaches:** in userspace mode, a connection from the tailnet is handed to 127.0.0.1 (or ::1) in the container by Tailscale's user. The entry's iptables rules let that user reach the shared ports on loopback, and the nameservers, and send replies on connections it didn't start (its proxy's, to the agent), and nothing else, so the gate, the browser and the runner's own servers stay out. Shared ports are below 20000 and never 7800, 7801, 7810, 7900, 7901 or 1055. If the rules can't be set, for IPv4 or for IPv6 where the container has it, Tailscale doesn't start, and the settings say why.
- **What the agent reaches:** the tailnet, through Tailscale's SOCKS5 and HTTP proxy on `127.0.0.1:1055`, which also resolves MagicDNS names. Nothing else changes for it: its traffic doesn't go through Tailscale unless it asks. It can't open the control socket (in a folder only Tailscale's user can), so it can't sign the machine out, `tailscale serve` anything, or read the key.
- **On Windows:** the same, but for who runs what. tailscaled's named pipe is open to every user, so it's kept by owning it: the entry runs `tailscale.ts` and `tailscaled` as SYSTEM, and the `tailscale` command as a hidden user of its own (`nibblet-tailscale`, through `nibblet-runas.exe`), whose `up --unattended` makes it tailscaled's owner. tailscaled then turns away every other user's connection, the agent's included. The pipe is under `ProtectedPrefix\Administrators`, where only an administrator can make one, so nothing can pose as tailscaled to be sent the key. Windows' firewall rules don't see loopback, so the fence is the Filtering Platform's: `nibblet-fence.exe` (`apps/runner/src/machine/windows/fence.cs`) lets `tailscaled.exe` connect over loopback only to the shared ports, with persistent filters set before it starts. Its binaries come from Tailscale's own signed installer, unpacked by the image's bootstrap, and its state is in `C:\ProgramData\Nibblets\tailscale`, SYSTEM's alone.
- **State:** the machine's keys live on a volume of their own (`nibblet-tailscale-<id>` at `/var/lib/nibblet-tailscale`), not the home volume, where the agent could swap in state of its own. It isn't snapshotted, and it's deleted with the nibblet. Once joined, the machine stays signed in across restarts, so a one-off key is enough. A different key, or OAuth client, signs out and joins again. Taking a nibblet off the tailnet, or deleting it, signs its machine out and empties the volume: its own container does it when it restarts, and while it's asleep a short-lived one (`entry.ts tailscale-leave`, with only that volume) does.

### Background tasks and terminals

- **Background tasks:** the runner serves a local `tasks` MCP server (`apps/runner/src/tasks.ts`), as it does `files`: `task_start`, `task_list`, `task_output` and `task_stop`. Each task is `bash -lc <command>` in its own process group, as the agent's user, with its output in a log under `/tmp`. It outlives the turn that started it, but not the container. A task is running for as long as anything in its process group is, so a script that starts a server with `&` and returns still shows (and stops) as running. When the container stops, tasks get SIGTERM and 8 seconds to finish (time for a game server to save) before SIGKILL; the server stops runner containers with `docker stop -t 12` for that. Logs are cut back to their last megabyte once they pass 16 MB. The runner sends the list to the server (a `tasks` message) whenever it changes and on every connect; the server passes it to the UI as a `tasks` live message, and `nibblets.tasks` answers the first ask. The user stops one with `nibblets.stopTask`, which the server passes on as `task_stop`.
- **Terminals:** the UI opens a WebSocket at `/api/nibblets/:id/terminal?cols=&rows=[&task=]`, with a ticket like the live socket. The server carries it over the runner's socket (`terminal_open`, `terminal_input`, `terminal_resize`, `terminal_ack` and `terminal_close` down; `terminal_output` and `terminal_exit` up), so there's no new port in the container. The runner starts a login shell, or `tail -F` of a task's log, in a pseudo-terminal through `terminal-pty.py`, since node-pty would need a compiler the image doesn't have. It runs as the agent's user, so it reaches what the agent reaches and nothing of the guard's. The browser acknowledges output once xterm.js has drawn it, and a terminal stops reading when more than 512K characters are unacknowledged, so a flood (`yes`, a huge `cat`) can't pile up in the runner, the server, or in front of a turn's messages on the same socket. The terminal ends when its shell exits, even if a background job still holds it open. A runner can only answer terminals opened on it, and terminal output is never kept for a reconnect: when the socket drops, the runner hangs up every shell.

### Borrowing the browser: a quick local sign-in

Signing in to a site through the nibblet's own browser is slow — no password manager, a remote window. So the user can borrow the nibblet's profile onto the machine running the server's host bridge (the desktop app), sign in there, and hand it back. The flow is in `apps/server/src/borrow.ts` (class `Borrow`), with the host end in `packages/host-mcp/src/browser.ts`.

- **Disabling the browser:** the whole nibblet is stopped for the borrow (`nibblets.browserBorrowStart`). Stopping it is what releases Chromium's hold on the profile and keeps anything from browsing the same logged-in session twice at once. While it's borrowed, nothing starts its container: heartbeats, schedules and its sub-agents' turns don't wake it, and `nibblets.start` is refused (`Conductor.borrowed`, checked against the container's own nibblet, so a sub-agent counts too). The UI asks for a second click when it, or one of its sub-agents, is working.
- **Pulling the profile:** stopped, the server copies just the profile (`/home/nibblet/.guard/.config/chromium`, caches left out) out of the home volume as a gzipped tar through a throwaway container (`archiveProfile` on the nibblet's machine plugin, mirroring `archiveHome`; only `DockerMachines` has it so far), and streams it to the host bridge. One whose browser never ran gets an empty profile, owned by the guard.
- **On the host:** `POST /browser/borrow` extracts the profile to a temp folder and opens it with `--user-data-dir` set to the copy, in the first Chrome, Chromium, Edge or Brave it finds (one that can load 1Password first, when that's wanted). It passes `--user-agent` so the window looks like the nibblet's Chromium (the UA is worked out from the runner image's Chromium version, `Orchestrator.browserUserAgent`), and `--proxy-server` so it browses through the nibblet's connection.
- **Cookies and passwords:** Chromium encrypts them with a key that depends on where it runs. The nibblet's, with no keyring, uses Linux's fixed key; Chrome on a Mac uses the Keychain's. So the host starts the window with a fixed key of its own (`--use-mock-keychain` on a Mac, `--password-store=basic` on Linux), and `profile-crypt.ts` re-encrypts every cookie and saved password into that key on the way in, and back into the nibblet's on the way out. A host browser newer than the nibblet's Chromium can upgrade those databases past what it reads; the bridge compares their versions before and after and refuses the handback if so, rather than hand over a profile that would come up signed out.
- **The window closing:** the browser is started with `--remote-debugging-pipe`, which only the bridge holds. On a Mac, closing the last window leaves the browser running, so the bridge watches its pages over the pipe and asks it to quit once there are none.
- **1Password:** only if it's installed here, and only in a browser that still honours `--load-extension` (Google Chrome dropped it in 137; Chromium, Edge and Brave keep it). The host's 1Password browser extension (found in a browser's default profile) is loaded into the window, with 1Password's native-messaging manifests copied into the borrowed profile, since a browser with its own `--user-data-dir` looks for them there; that's how the extension reaches the 1Password app. The UI only says 1Password is in the window when it will be. Before the profile is handed back, **every** extension and its state is purged from it, 1Password included, so the nibblet never receives it: a headless run of the same browser clears each extension's origin (`Storage.clearDataForOrigin`: IndexedDB, local storage, service workers and the rest, which share stores with websites), then `purgeProfileExtensions` deletes the extension folders, their settings, and the `extensions` block of the preferences.
- **The proxy:** a tiny HTTP/HTTPS forward proxy runs in a container on the nibblets' Docker network (`Orchestrator.startBorrowProxy`), published only on the host's loopback, so the borrowed window egresses from the same place the nibblet would (its public IP). Anything on the host can reach that port, so the proxy carries a runner's firewall: it refuses its own network (other nibblets, the server) and link-local addresses (cloud metadata), checking each address a name resolves to. A Tailscale exit node isn't reproduced: that lived in the now-stopped container. Proxies a stopped server left behind are removed when it starts again.
- **Handing back:** closing the window hands the cleaned profile back. The server unpacks it beside the old one and swaps it in only once it's whole (`restoreProfile`, handing ownership back to the guard), so a broken or cut-off handback leaves the old profile alone; the bridge breaks the connection, rather than ending it, if packing fails part-way. The request waits as long as the window is open, so it's made without fetch's usual time limit. The nibblet is started again if it was awake before. `nibblets.browserBorrowEnd` ends it early, throwing the local sign-in away. State rides the `browser_borrow` / `browser_borrow_ended` live messages, the latter saying why it failed if it did, which the UI shows; `nibblets.browserBorrow` answers the first ask. It needs the host bridge, so it's the desktop app only, and the window opens on that computer, so "Sign in locally" isn't offered to a browser reaching the UI over Connect from somewhere else.
- **Which machines:** only those whose capabilities say `localSignIn`, which for now is containers. A VM's profile would need its guest agent to pack it, a Windows or macOS guest's browser encrypts with a key of its own, and the proxy lives on the containers' Docker network; `Borrow` refuses the rest, and the UI doesn't offer it.

### OpenCode

OpenCode nibblets use the host's own OpenCode account, not the credential proxy. The host bridge reports whether OpenCode is set up (`GET /harness/opencode`: the CLI, OpenCode.app, or a config or login in its XDG directories) and hands over the config and `auth.json` (`GET /harness/opencode/login`, bridge token only).

- **The model picker:** `harnesses.models({ harness: "opencode" })` lists whatever OpenCode offers for that login. The server runs `apps/runner/src/opencode-models.ts` in a throwaway runner container with the login on stdin, so the list is exactly what a nibblet will see, and caches it for a minute. The host doesn't need the CLI.
- **On each configure:** the server fetches the login fresh, keeps only the entry for the nibblet's model's provider, and sends it only over the runner socket. The runner writes the config into the container, and the login to `/tmp/nibblet-secrets/opencode-auth.json`, with OpenCode's `auth.json` a link to it, so it never lands in the home folder or its snapshots.
- **What changes in the container:** the host config's `mcp` section is dropped, because the nibblet brings its own servers. Provider URLs on the host's `localhost` or `127.0.0.1` are pointed at `host.docker.internal`, so a local Ollama still resolves.
- **Not written back:** a provider whose OAuth token refreshes inside the container doesn't write it back to the host.
- **Without a bridge or a login:** OpenCode falls back to Anthropic and OpenAI through the credential proxy.

### DeepSeek

DeepSeek nibblets are the Claude harness on DeepSeek's Anthropic-compatible API. `@nibblets/harness-deepseek` is a few lines on `claudeCodeHarness` from `@nibblets/harness-claude`, the same Claude Agent SDK loop and mapper, with the base URL set to the proxy's `/deepseek` route instead of `/anthropic`.

- **The CLI:** it runs Claude Code, so it has no CLI of its own (`cliOf: "claude"`). The updater lists and installs Claude Code once, under Claude, and DeepSeek nibblets use that one too.
- **Models:** V4.1 Flash (`deepseek-flash`, which DeepSeek keeps on its newest Flash) and V4 Pro (`deepseek-v4-pro`), both with DeepSeek's effort levels (`low`, `high`, `max`). Effort is only sent for a level the model declares, so `medium` is left to DeepSeek. Only Flash takes images; V4 Pro gets their paths. Claude Code's own background work runs on Flash (`ANTHROPIC_DEFAULT_HAIKU_MODEL`).
- **Offered:** once the proxy reports a key, like Claude and Codex once their subscriptions are signed in. Its Settings row only shows once a key is set.

### Kimi Code

Kimi nibblets use the host's own Kimi Code CLI login, like OpenCode ones. The host bridge reports whether Kimi Code is set up (`GET /harness/kimi`: the `kimi` CLI on PATH, or a `config.toml` or token under `$KIMI_CODE_HOME`) and hands over the config and the OAuth token (`GET /harness/kimi/login`, bridge token only).

- **On each configure:** the server fetches the login fresh and sends it only over the runner socket. The runner writes the config into `<workdir>/.kimi-code/config.toml`, and the token to `/tmp/nibblet-secrets/kimi-code.json`, with `credentials/kimi-code.json` a link to it, so it never lands in the home volume or its snapshots.
- **What the CLI is asked for:** one process per turn, `kimi -p <prompt> --output-format stream-json`, which never asks for approval, so nothing waits on a person who isn't in the container. The stream is OpenAI chat shaped, which `KimiMapper` turns into thread items; sessions live on disk and the next turn resumes with `--session`.
- **What changes in the container:** the nibblet's own MCP servers go in `<workdir>/.kimi-code/mcp.json`. Because that path is also where Kimi looks for a project's servers, the turn runs with `KIMI_CODE_TRUST_WORKSPACE=1`, the same trust the other harnesses give their workdir.
- **Without a bridge or a login:** the harness says so rather than guessing at credentials. Kimi Code has no credential proxy to fall back to.
- **Effort:** OpenCode has no effort setting, so its models carry none and the effort menu is hidden.

## Machines: containers and virtual machines

Where a nibblet runs is a plugin. `@nibblets/machine` is the base: `MachinePlugin`, the contract the conductor uses for everything it does to a nibblet's machine (start, stop, reach a port in it, run its sub-agents, archive its home), and `MachineRegistry`, which loads the plugins and routes each nibblet to its own. A nibblet records its `machine` (`{ backend, guest }`) when it's made; it never changes, and sub-agents run in their host's.

| Plugin                      | Runs on                     | Machines                                       | Guests                        |
| --------------------------- | --------------------------- | ---------------------------------------------- | ----------------------------- |
| `docker` (`machine-docker`) | the server, on Docker's API | containers from the runner image (recommended) | Linux                         |
| `apple` (`machine-apple`)   | the host bridge, on a Mac   | Virtualization.framework, through `nibblet-vm` | Linux; macOS on Apple silicon |
| `hyperv` (`machine-hyperv`) | the host bridge, on Windows | Hyper-V, through PowerShell                    | Linux, Windows                |
| `kvm` (`machine-kvm`)       | the host bridge, on Linux   | KVM through QEMU                               | Linux; Windows on x86         |

What each can do differs (`MachineCapabilities`): only containers share the host's SSH agent and change size while they run, and every guest has the browser and Tailscale, and Windows and macOS guests a desktop of their own. The conductor turns off what a machine can't have, and the UI says so.

### Virtual machines

The server is in a container, so it can't drive a hypervisor. VM plugins run in the host bridge (`HypervisorPlugin`, loaded by `hostMachines` for the bridge's OS), which serves them at `/machines` (`bridge-api.ts`); the server has one `VirtualMachines` plugin per hypervisor, which speaks to it. The bridge keeps each VM's folder (its disks, `vm.json` with its size and boot, its console) under its data directory, `machines/<hypervisor>/vms/<id>`, and VMs outlive it: Apple's are each a detached `nibblet-vm run`, KVM's a daemonised QEMU, and Hyper-V keeps its own.

- **The guest agent** (`apps/runner/src/machine`): a daemon the guest starts at boot, as root (SYSTEM on Windows), on a port of its own: vsock on Apple (a virtio console there, a tty, stalled for good on a Linux guest's first boot), a named virtio serial port on KVM, COM2 for Windows on KVM, and a Hyper-V socket on Hyper-V. Node can't open a socket of either kind, nor set up a COM port, so small relays do it over stdio: the host's own `nibblet-vm guest-relay` for macOS, `nibblet-serial.exe` for Windows' COM port, a Python script in Linux guests (connecting to Apple's host, or listening for Hyper-V's), and `nibblet-hvsock.exe` in Windows ones on Hyper-V, with a helper the bridge builds with Windows' `csc` on the host's side. A guest's relay takes only its host's connections, so nothing in the VM can pose as the host. The hypervisor plugin hands the host's end to the bridge, which relays it to the server over a WebSocket the server opens (`/machines/:hv/vms/:id/link`). Over it (protocol's `guest.ts`) the server does what `docker exec` does for a container: runs the entry's commands (`main`, `subagent`, `stop-subagent`, `archive-home` and the rest), signals them, and reads the end of their output, and opens connections to ports in the guest for the browser's view.
- **No route to the host:** the agent listens on the guest's loopback for `server` and `credproxy` (its hosts file points them there), and each connection the runner makes goes out over the port, for the bridge to make on the host (`GuestRelay`). The port is only the guest's and the hypervisor's, so nothing in the guest holds a key, and the entry's firewall fences off the VM's network as it does a container's (the host's address is let through, as `host.docker.internal` is for a container). Windows' COM port on KVM is slow next to a virtio one, so the browser's view and snapshots are too there.
- **Disks:** each VM has a system disk, made from its guest's image (an APFS clone on a Mac, a qcow2 overlay on KVM, a differencing VHDX on Hyper-V) and replaced when the image changes, and a home disk, kept until the nibblet is deleted, which the agent formats the first time and mounts over the agent's home. Snapshots of a VM that's off boot it for the job, without starting the nibblet.
- **Starting:** `VirtualMachines.start` makes sure the guest's image is made and current, boots the VM, waits for its agent, and runs the entry. CPUs and memory are fixed while it runs (whole CPUs, up to 4 when there's no cap).

### Guests' images

- **Linux** (`linux-image.ts`): the runner image itself, with a kernel, systemd, networkd and the agent's service added, built with the host's Docker CLI and laid out as an EFI disk (systemd-boot, and an ext4 root made with `mke2fs -d` straight into the disk at its offset) in a throwaway container, with no root or loop devices. Made by itself on first start, and again when the runner image changes. It checks there's room first: about 12 GB. On arm64 it boots with `arm64.nosme`, and there's no memory balloon, both for M-series Macs.
- **Windows** (`windows-image.ts`, Hyper-V and KVM): from the user's own installer ISO, given in Settings. A setup disc made here (`iso.ts`, since Windows hosts have no tool for it) answers setup (`autounattend.xml`), which installs Windows without asking, and at `specialize` sets `bootstrap.ps1` to run at every startup as SYSTEM: it installs Node 24 and the release's runner from GitHub, builds `nibblet-runas.exe` and `nibblet-serial.exe` (`machine/windows/*.cs`) with `Add-Type`, and runs the agent. While the image is being made, it shuts down instead. In the guest, the guard runs as SYSTEM and the agent as a hidden local user; stopping is at once, since Windows has no SIGTERM for a console process.
- **macOS** (`machine-apple`, Apple silicon): the newest macOS Apple offers this Mac, downloaded and installed by `nibblet-vm macos-install`, then booted once for the system to set itself up. macOS has no answer file, so its Data volume is mounted on the host (with `mount_apfs`: DiskArbitration refuses it) and given a LaunchDaemon (`bootstrap.sh`), the VM helper, the mark that setup's done, an `/etc/fstab` line that mounts the home disk over the agent's home at boot, a LaunchAgent for the login window's own session, and permissions in its privacy database (which the running guest's own root can't change): Accessibility and Screen Recording for OpenComputerUse, and Full Disk Access for the guest agent's Node, each tied to its developer's signature. That takes an administrator's password, once, which macOS 27 asks for in its own words. Then one boot installs Node, the runner, OpenComputerUse and Google Chrome (each checked against its developer's signature), and Tailscale, built from source with Go, saying each step to the host over vsock and stopping at the first that fails. Each VM gets a machine identifier of its own, at least 4 GB of memory, and a console on vsock port 1025. In the guest, the agent, the guard and Tailscale are hidden users of their own. macOS 27 signs a user in only at boot, and only with an automatic login turned on from the login window's session, so the guest agent's first boot (of a VM, or of a new image) has the LaunchAgent turn it on, with a password kept on the home disk (so the login keychain opens whichever image it boots), and restarts; every boot after signs the agent's user in to its own home. OpenComputerUse (the browser's and the desktop's) runs as it in that session, which the guard reaches through one sudo rule for the session script, launched through `nibblet-vm disclaim` so macOS asks OpenComputerUse, not the guest agent, for its permissions. The home's archive leaves out Mac metadata, which tar can't always read back, and what macOS fences off even from root. pf fences off the VM's network and, on a tailnet, what Tailscale's user may reach on loopback.

Windows and macOS guests install the runner from the release the server runs (`v<version>` of `NIBBLET_UPDATE_REPO`), so they need a release with this in it.

## Bank: cards and wallets

A nibblet can be given money to spend, as virtual cards or as crypto wallets that work like them. Where the money comes from is a bank plugin (`packages/bank-*`) implementing `BankPlugin` from `@nibblets/bank`: it issues a card with a lifetime limit, gives its details again (`reveal`), reports what's been spent on it (`inspect`), and closes it (`close`). Each plugin's factory describes its own settings form (`fields`: labels, hints, secrets, choices, keys the form can make, and fields that can't change while cards are open), so Settings → Bank sets any of them up without the web app knowing one bank from another. Saving checks the settings with the provider (`check`), keeps them in the `settings` table (`banks`, secrets never sent back), and loads the plugin without a restart (`apps/server/src/banks.ts`, which lists the plugins). There can be several banks on one plugin (two Slash accounts, or a signet and a mainnet treasury), each with its own id, settings and name; one per plugin can go without a name. The first bank on a plugin gets the plugin's own id (`slash`) and later ones one from their name (`slash-travel`), and a card keeps its bank's id, so renaming a bank never strands its cards. A plugin with no saved bank under its own id also gets one from the server's environment, whose variables are named like its fields. A plugin holds its provider's credentials, which never leave the server. Settings shows each bank, its balance, where to top a treasury up (`fundAt`), and any whose settings are wrong. A bank can't be removed, or have its locked fields changed, while it has cards that aren't closed.

- **Limits:** the person sets each nibblet's `spendingLimits`, one per asset (`USD`, `BTC`, `ETH`), per day, week or month (UTC) or in total. A nibblet has none to begin with, so it can't have a card until it's given one, and it can't change its own. Every card counts against its period for its whole limit while it's open, since it could all still be spent, and for what was spent once it's closed. One request or kill at a time per nibblet, so two at once can't both fit the same budget.
- **The card file:** `card_request` asks the plugin for a card, stores its record (`cards`: never the number or key), and sends its details over the runner socket (`card_put`). The runner writes them to `$TMPDIR/nibblet-cards/<id>.json`, `0600` in a `0700` folder, as the agent's user, and answers `card_done` with the path, which is all the tool returns. So a card's number reaches the model only if it reads the file, and never the thread, the database or a snapshot. A card that can't be written is closed again. The folder goes with the container; when a runner reconnects, the server asks the plugins for its open cards again and rewrites them.
- **Card states:** a card's row goes in as `pending` before the plugin is asked for it, so one the provider made before something failed (a timeout after it was sent) is never lost: every minute the server asks the plugin to `find` pending cards it isn't still making, closes any that were made, and forgets ones that haven't shown up in an hour. A plugin throws a `BankError` only for a refusal, where nothing was made; its message is the only kind passed on, since other errors can carry credentials (an RPC URL with its key), so they're logged on the server instead.
- **Closing:** `card_kill` (the nibblet, its own cards), Kill in the UI (the person, any), and deleting a nibblet close cards at the provider and delete their files. A card the provider can't settle yet (a wallet whose funding isn't seen, so there's nothing to sweep) stays `closing`, counting in full, and the server tries again every minute; after a day it's recorded as closed with a warning in the log. A nibblet with a card that can't be closed isn't deleted, so the card's record (and a wallet's id, from which its key comes) isn't lost. Every minute the server also checks open cards with their providers: it records what's been spent, notices cards the provider closed, and closes single-use cards that have been used where the provider doesn't do that itself.
- **Slash** (`packages/bank-slash`, `USD`): virtual cards on the person's Slash account, set up with `SLASH_API_KEY` (with the cards.view and cards.manage permissions), plus `SLASH_ACCOUNT_ID` for the account cards are made under and whose balance Settings shows (Slash picks the first commercial account otherwise). Single-use cards are Slash's own `isSingleUse`, which Slash closes after the first authorisation; both kinds carry a `collective` (never resetting) utilisation limit of the card's limit, so Slash declines anything over it. Each card is tagged with its id in `userData`, which is how `find` recognises it.
- **Stripe** (`packages/bank-stripe`, `USD`, `EUR` or `GBP`): virtual cards from Stripe Issuing, set up with `STRIPE_API_KEY` (a secret key, or a restricted one that can write Issuing cards and read cardholders, authorizations, transactions and balances) and `STRIPE_CARDHOLDER_ID` (the `ich_` cardholder cards are made for, whose billing address goes in each card's file), plus `STRIPE_CURRENCY` for an Issuing balance that isn't in US dollars, and `STRIPE_WEBHOOK_SECRET` to approve each purchase (below). Each card carries an `all_time` spending limit of the card's limit, so Stripe declines anything over it. Stripe has no single-use cards, so a single-use one counts as used once anything but a zero-amount check has gone through it, and the server cancels it. What's spent is captures net of refunds plus authorisations not yet captured. A card whose number Stripe won't hand over is cancelled again as soon as it's made. Taking live card numbers over the API puts the server, and wherever a card's file is read, in scope for PCI DSS: Stripe's own advice is to keep them to its Dashboard and Issuing Elements. Each card is tagged with its id in `metadata`, which is how `find` recognises it.
- **Approving each purchase:** a plugin whose provider can ask before each purchase says where its form is (`purchaseHook` on the factory), and a bank set up to answer has `purchases` (Stripe's real-time authorizations, once `STRIPE_WEBHOOK_SECRET` is set). The provider posts to `/bank/<plugin>/purchases`, which nobody signs in to: each bank on that plugin checks the request's signature (`read`), and the one that signed it says which card it's for. Banks on one Stripe account share its one webhook and so its secret, so the card is looked for at every bank that signed the request. The server approves only if that card is open, the purchase is in its asset and fits what's left of its limit, counting what it approved since shortly before the card was last checked with the provider (which may not have shown those yet), and a single-use card makes only one purchase, though that one can ask for more on the same authorisation (a hotel stay running on) and zero-amount checks don't count. The provider asks about every card on the account, so a purchase on a card that isn't a nibblet's (one without the server's tag, Stripe's `metadata`) is approved, leaving it to the provider's own rules, while one tagged as a nibblet's that this server doesn't know is declined. Anything it can't read or check is declined, and so is everything when the server can't be reached, as long as the person has set the provider to decline when it gets no answer (Stripe's timeout setting, in its Dashboard). The provider reaches the server at its public address (below); Settings → Bank shows the address to give the provider, and warns that a quick tunnel's changes whenever it starts.
- **Verifying a payment:** when a checkout asks to verify the payment (3-D Secure: a code sent by text or email, or the bank's own page), the nibblet calls `card_verify` and leaves the page alone. That's an approval in its thread, which notifies the person; they open its browser, do the verification there themselves, so the code never reaches the model, and press Done or Couldn't. Meanwhile the nibblet's status says what it's waiting for, and goes back to what it was once they've answered. A tool call that waits too long is dropped by some harnesses (Codex gives up after a minute), so `card_verify` returns after about 40 seconds if they haven't answered, and the nibblet calls `card_verify_wait` to wait again. This works for any bank's cards.
- **Wallets:** a crypto plugin funds a fresh wallet per card from its treasury with exactly the card's limit, so the limit holds on chain. The wallet's key is derived from the treasury's secret and the card's id (`deriveWalletKey`), so none is stored, and killing the card sweeps what's left back to the treasury.
- **Bitcoin** (`packages/bank-bitcoin`, `BTC`): `BITCOIN_TREASURY_KEY` (hex or WIF) and `BITCOIN_NETWORK` (`mainnet`, `testnet`, `signet` or `regtest`, with no default, so a test key never lands on mainnet by accident), plus `BITCOIN_ESPLORA_URL` (mempool.space's API by default; needed for regtest) and `BITCOIN_FEE_RATE` (sat/vB, instead of Esplora's estimate). The treasury and every card wallet are native segwit (P2WPKH), signed with `@scure/btc-signer`. A card needs at least 5,000 sats.
- **Ethereum** (`packages/bank-ethereum`, `ETH`): `ETHEREUM_TREASURY_KEY` and `ETHEREUM_RPC_URL`, plus `ETHEREUM_CHAIN_ID` (checked against the RPC before anything is sent) and `ETHEREUM_ASSET` for another EVM chain's coin (`POL`, say). Plain transfers, signed with `viem`. Gas comes out of the card's own balance. The sweep pays exactly 21,000 gas at the current price, so chains that also charge an L1 data fee (Base, Optimism and other OP Stack chains) aren't supported yet: their sweeps would fail, and killed cards would stay `closing`.
- **What a wallet can't do:** a nibblet holds its wallet's key, so it can spend all of the wallet's limit, and nothing more, the moment it has it; network fees, the sweep's included, count as spent. Killing a card sweeps what's left, but a nibblet that copied the key before could race the sweep for it, so treat a crypto card's limit as given away.

## App links: identities in other apps

A nibblet can act in another app as itself, rather than as its person. In Infrawrench, say, it becomes an agent of its own in an organisation: its own credential, its own name in the audit log, and only the scopes the person ticks. Before this, a nibblet could only reach Infrawrench through its MCP server with the person's own login, which gave it everything they could do.

Each app is a plugin (`packages/app-link-*`) implementing `AppLinkFactory` from `@nibblets/app-link`. A factory says what the app is called, a line about it, its logo (a `data:` URL), and the settings it needs before linking (`fields`, such as the app's address, with a default). The plugin it makes knows everything about the app: how to link, what a link may grant, how to make, change and revoke a grant, and how a nibblet reaches the app with one. So the server (`apps/server/src/app-links.ts`, which lists the plugins) and the web app never know one app from another, and adding an app is adding a plugin.

- **Linking, once per server:** Settings → Linked apps starts it (`appLinks.begin`). The plugin either asks the app for a code, like `gh auth login` (`via: "code"`), or has the person sign in there (`via: "sign_in"`); the UI opens the app's page in a new tab, and shows the code if there is one. That page is only ever an http or https address, checked by the server and again by the UI before it's opened or linked to (Infrawrench's and T3 Code's must also be on the app's own address), so an app can't hand the UI a `javascript:` URL. The person approves it there, choosing what the link may ever grant. For a code, the server polls the app at the interval it asks for (longer after `slow_down`). Signing in is OAuth from `@nibblets/oauth`, and the app sends the person back to the server's `/api/app-links/callback`, a plain page load that isn't signed in: the state it brings back says which attempt it finishes, and only one the server started and is still waiting on, once. The page says how it went. Its address is the one the UI reached the server at (`serverUrl`, sent with `begin`) when an app would send someone there (https, or this computer), else the server's public address (its reverse proxy, or Nibblets Connect's tunnel); with neither, the plugin says it can't link. Either way the server says how it went with an `app_link_settled` live message. Attempts are kept in memory only: one a restart cuts short is started again. The link's secret goes in `app_links`, beside the account it's linked as and the name its tools go by (the plugin's id, then `infrawrench-2` and on for more links on one plugin, never a built-in's).
- **Adopting, when the app set the server up:** an app that made this server itself (Infrawrench, provisioning a machine for Nibblets while its person is signed in there) can approve the link up front and hand it over, so the server starts out linked with no code. The installer reads `NIBBLETS_APP_LINKS_FILE`, a 0600 JSON list of `{ plugin, settings, secret }`, rather than a variable or an argument, which other users could see in `ps`. Once the stack is up it passes each to `appLinks.adopt` with the owner token, both kept off the command line (the token in a curl config on a pipe, the body on stdin), and deletes the file once every link has been taken; until then it's kept, 0600, for running the installer again. Only the owner token may adopt, not a paired device. The plugin checks the secret with the app (`adopt`, optional: an app that only links with a code leaves it out; Infrawrench's asks `GET /api/agent-link`) and says who it is, as a settled poll would, and the link is kept as one made here. A link the server already has (the same plugin and the app's own id for it) is brought up to date with the newest secret rather than kept twice, so running the installer again is safe. One that's being removed isn't taken back.
- **Granting, per nibblet:** in a nibblet's settings, each link has a switch and the scopes the app says it may grant (`appLinks.describe`, grouped and named by the app, with the providers a grant can be narrowed to). Saving (`nibblets.setAppGrant`) asks the app for a credential of the nibblet's own, with the nibblet's id as the app's `externalId`, and keeps it in `nibblet_app_grants`. Saving again changes the same one. The app checks the scopes against the link, and its refusal is shown as it says it. A sub-agent uses its host's grants, and can't have its own.
- **Grants the gate keeps:** an app that can't make a credential per nibblet (T3 Code) has its factory say `grants: "gate"`. Then a grant is only what the gate lets a nibblet do with the link's credential: `connection` gets the link too, and names the tools the grant gives (`AppLinkServer.tools`), so the gate lists and allows only those, and answers a call of any other with an error before asking anyone. Such grants aren't the app's to revoke: the regular check doesn't look for them, and when the link is revoked they're kept but not handed out, and work again once it's linked again (with the new credential, since keeping a link the server already has hands its nibblets their servers again).
- **Where the secrets go:** the link's and each grant's stay on the server, like a nibblet's MCP headers, and are never in what the API returns. A grant's reaches only its nibblet's guard: `GuardConfig.appLinks` has one MCP server per grant, under the link's name, with its credential in its headers. The runner and the harness only get the name, among the gate's. So "ask me first" rules apply to its tools as to any other server's, and one of the nibblet's own servers with the same name is left out while the link has it. The prompt says which apps it's linked to, as whom, with which scopes, and what the plugin adds.
- **Revoking, from either end:** turning a nibblet's switch off revokes its grant in the app, and deleting a nibblet revokes all of its. Unlinking (`appLinks.remove`) asks the app to revoke the link, which takes every grant on it along. When the app can't be reached, the grant is kept as `revoking` (or the link as `removing`), no longer handed out, and tried again every five minutes for a day; after that it's dropped with a warning in the log, to be revoked in the app. Grants aren't tied to their nibblet's row for this reason: a deleted nibblet's can outlive it until the app has been told. The other way, the server asks each link's app every five minutes which of its grants it still has live. An app answering 401 for a link marks it `revoked`, and its grants with it; a grant the app no longer knows is marked `revoked` too. Either way the nibblet's guard is handed its servers again without it, and the UI says so. Saving a revoked grant again makes a new one.
- **Errors:** a plugin throws an `AppLinkError` for what the app refused, whose message is shown, and an `AppLinkRevokedError` for a link or grant the app revoked. Anything else is logged on the server and shown as the app not answering, since it can carry a credential.
- **T3 Code** (`packages/app-link-t3code`): over the MCP server each T3 Code environment serves at `/mcp` for agents it didn't start, with the MCP SDK's client. Its address is a setting, with no default: T3 Code runs on the person's machine, so it's the environment's T3 Connect address or another https one (its "Copy MCP URL", with or without `/mcp`), and must be https except on this computer. The nibblet reaches it from its container, so `localhost` there isn't the person's computer. Linking is signing in: it finds T3 Code's sign-in from its protected resource metadata, registers the server's callback address (T3 Code's registration is stateless, so it's done each time), and asks for `orchestration:read` and `orchestration:operate`. The person approves on T3 Code's page with a pairing code from its Settings → Sharing & access, choosing read only or how much a thread may do, and the token's scopes say which. It's the link's credential, kept with them and when it runs out (in 30 days; there's no refresh), and the link's id is the environment's, from `t3_environment_read`. Grants are the gate's, one scope per tool, grouped by T3 Code's systems (threads, attachments, projects, pull requests, scheduled tasks, the environment) in `tools.ts`. That catalogue is kept by hand from T3 Code's source, saying the version it's from: it leaves out the tools only a T3 Code thread can call (delegating, previews, devices and the like, which refuse an outside agent), and says whether each reads, changes, or both. A link T3 Code approved read-only offers only the ones that read (or both, whose changes T3 Code refuses). A tool T3 Code adds reaches no nibblet until it's added there. A sign-in that has run out, or that T3 Code answers 401 to, revokes the link until it's linked again. T3 Code has no route to sign out, so unlinking forgets the link here only; its description says to revoke it in T3 Code. Commands and file changes a thread asks to make are approved in T3 Code's own app, since its MCP server won't answer them, which the prompt tells the nibblet. Its logo is T3 Code's own (`assets/prod/logo.svg`), an SVG.
- **Infrawrench** (`packages/app-link-infrawrench`): over Infrawrench's agent link routes (`/api/agent-links/requests*` to link, then `/api/agent-link*` with the link's `iwl_` credential). Each grant is an agent with its own `iwa_` credential, which the nibblet uses on Infrawrench's MCP server (`/api/mcp`). Narrowing to providers is Infrawrench's: it rewrites each `resources:*`, `secrets:*` and `storage:*` scope for those plugins, and with any provider chosen refuses every other scope, which would still reach every provider. It says which those are (`narrowableScopes`, the description's `narrowable`), so a nibblet's form unticks and turns off the rest once a provider is ticked. A link holds at most 200 live agents, and the form says so when it's full. If Infrawrench already has a live agent for the nibblet (one this server lost track of), it's revoked to make way, since nobody holds its credential. Its address is a setting, `https://app.infrawrench.com` unless it's self-hosted, and must be https except on this computer. Its icon is Infrawrench's own app icon, a painting rather than a drawing, so a PNG.

## MCP Apps: views in the chat

An MCP server can give a tool a view: HTML the chat shows with the call's input and result, which the person can use, following [MCP Apps](https://modelcontextprotocol.io/extensions/apps). The tool names a `ui://` resource in its `_meta.ui.resourceUri` (or the older `_meta["ui/resourceUri"]`), served as `text/html;profile=mcp-app`. This works for every server behind the gate: app links, the nibblet's own servers, the browser and 1Password. Host servers (`host_*`) aren't behind it, so their views aren't shown.

- **Noticing them:** the gate notes each tool's view from `tools/list` (listing the server itself for a tool it hasn't seen). When the agent calls one, the gate answers the agent as usual, then reads the view with `resources/read` and posts it with the call to `/guard/:id/view` (`GuardAppView`). The server keeps the HTML, its CSP and permissions in `app_views`, by a hash of them per nibblet, so every call of a tool shares one row, and puts an `app_view` item in the thread with the input, the result and the view's id. A view over 2 MB, or a call whose input and result are over 1 MB together, isn't kept. A tool whose `visibility` is only `app` is left out of the agent's `tools/list`, and its calls from the agent are refused.
- **Drawing them:** the web app fetches the view (`nibblets.view`) once it's nearly on screen and draws it in an iframe with `sandbox="allow-scripts allow-forms"` and no `allow-same-origin`, so it gets an opaque origin of its own and can't reach the page, its storage or the server. Its HTML gets a CSP first (`apps/web/src/lib/appViews.ts`): its own inline scripts and styles, and only the addresses its resource names (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`), each checked to be a plain web or socket address. Never `'self'`. Of the permissions it asks for, only `clipboardWrite` is given: the frame would otherwise inherit the camera, microphone and location the person gave Nibblets itself.
- **Talking to them:** `@modelcontextprotocol/ext-apps`' `AppBridge` speaks the protocol over `postMessage`. It sends the call's input and result once the view has initialised, the theme as it changes, and only `inline` as a display mode. The view can open web links (`openWeb`), and suggest a message (`ui/message`), which goes in the message box for the person to send or not, rather than being sent as them. Its height follows what it says, up to 720 pixels.
- **Their own calls:** a view's `tools/call` goes to `nibblets.viewCall` with its item's id, so it only ever reaches the server its view came from. The server sends `view_call` to the runner (`AppViews`, `apps/server/src/views.ts`), which calls the tool through the gate at `/app/<name>` rather than `/mcp/<name>` (`apps/runner/src/view-calls.ts`) and answers `view_call_done`. There the gate lists and allows only the tools a view may call, applies "ask me first" as for the agent, and doesn't report the call as a new view. The agent could reach `/app/<name>` too, since it shares a user with the runner, but that only gets it tools meant for views, still gated.

## Location: where its person is

A nibblet can ask where its person is, so it knows their town, their time zone and what's nearby. Their device answers when they say so, or by itself where they've allowed it, and they can share it from the nibblet's settings too.

- **From the device:** the web UI asks `navigator.geolocation` for a rough fix and sends it with the device's own time zone (`Intl`), since a position alone doesn't give one (`nibblets.update` with `location`, a `LocationFix`). Browsers only allow it on a secure page, so it works on `127.0.0.1`, through Nibblets Connect or a tunnel, and on Tailscale's https, but not on a plain-http LAN address; the settings say so. In the desktop app, Electron grants the permission only to the UI's own origins, and on macOS Core Location asks first (the app has the location entitlement and `NSLocationUsageDescription`). Electron on Linux has no location provider, so there the person shares from a browser.
- **The place:** the server looks up the place the position is in with Nominatim (`apps/server/src/geocode.ts`): OpenStreetMap's by default, or `NIBBLET_GEOCODER_URL`, empty for none. It sends the position rounded to about a hundred metres and asks at suburb level, so no street is ever named, and keeps to Nominatim's policy of one request a second with a User-Agent. It keeps the district, town, region, postcode and country beside the coordinates, accuracy and time zone (`location` on the nibblet's row). A failed lookup keeps the coordinates alone.
- **How the nibblet gets it:** with the `location_get` tool, which asks the person's device where they are now (`apps/server/src/location-requests.ts`). The ask is a `location_request` item in the thread, which every open UI hears over the live feed. A device the person has let answer by itself for that nibblet (a switch in its Location settings, kept in that browser's storage, since it's about where that device goes: a phone, not a desktop left at home) answers straight away if the browser already allows it the position (`navigator.permissions`). Otherwise the UI asks: Share or Not now in the thread, and in a box over the page anywhere else in the app (`LocationResponder`). The first answer wins (`nibblets.answerLocation`); it's looked up as above and kept as the nibblet's location (the top of a sub-agent's tree's, unless the sub-agent has its own). The tool waits up to 45 seconds, within harnesses' tool-call timeouts, and doesn't ask at all when no UI is open. Unanswered, it gives where they last shared, saying so and why; declined, it gives nothing. Stopping the turn or the nibblet gives up on the ask, and asks a restart left pending are closed. The tool is always offered, so it works before anything's been shared, and the location isn't in the prompt: once one's shared, the prompt just says to call the tool when it matters, and not to pass the answer on.
- **Its clock:** a container is started with `TZ` set to that time zone (the image has `tzdata`), so the shell's `date` and the browser's clock are the person's. Like the browser setting, that's fixed when the container is made: sharing from a new time zone changes it at the next restart, and the prompt has it right meanwhile.

## API

The typed contract is `contract` in `packages/protocol/src/contract.ts`. Calls are `POST /api/rpc/<dotted.path>`. Live updates are a WebSocket at `/api/live` pushing `LiveMessage`s. Browsers authenticate with `Authorization: Bearer <token>`; WebSockets take `?ticket=` from `POST /api/ticket`, which lasts 30 seconds, so long-lived tokens never go in URLs.

First run prints, and the desktop app opens, a pairing link `http(s)://host/#pair=<code>`. The UI exchanges the code at `POST /api/pair` for a long-lived token.

## Across machines: Nibblets Connect (`apps/connect`)

Each machine runs its own server. Like T3 Connect, a central service (a Cloudflare Worker with D1, signed in with Clerk) lists every server on an account, without being in the data path:

- A server links with a code approved on the central site, then sends a heartbeat every 30 seconds with its routes: local network (`NIBBLET_LAN_URLS`), Tailscale (`tailscale serve` through the host bridge), and a Cloudflare tunnel (a managed one when the central service has a zone, a quick one otherwise).
- Approving a link shows where the server asked from. If that's a different network from yours, you have to tick that you started it yourself, so a code sent by someone else can't quietly add their server to your account. Every device you're signed in on is told when a server is linked.
- The central UI (the web app built with `build:central`) tries each server's routes in that order with a `/healthz` probe, and talks to the first that answers with a five-minute ES256 token from the central service. Servers verify those tokens against its JWKS.
- The desktop app asks on first run whether to run a server on this computer. If not, it only shows the central UI.
- "Pair a device" still signs a device in to one server directly, on the same network.
- **Public address** (`apps/server/src/public-address.ts`, the `publicAddress` RPCs): how the server is reached from the internet, for anything that needs to be told, such as a card provider asking about purchases (above) or a pairing link. It's the person's own reverse proxy's address when they've given one under Remote access (the `publicProxy` setting), or else the tunnel's while it's up, or else none; pairing links fall back to `NIBBLET_PUBLIC_URL`.

See `apps/connect/README.md` for deploying it.

### Third parties: other companies' agents in the sidebar

Nibblets Connect can also list other companies' agents (Revnu and Notra) in the sidebar beside the person's nibblets, drawn like them: a logo where the hamster goes, a dot for how it is, and what's waiting on the person. Opening one shows its conversation and a panel of what it's waiting on, which the person answers there. They're the account's, not a server's, so they live in Connect alone, and a server of its own never shows them.

- **Plugins:** each third party is a plugin (`packages/third-party-*`) made with `defineThirdParty` from `@nibblets/third-party`. A factory says what it's called, a line about it, its logo (a `data:` URL), and how it's connected: signing in on its site (`signIn`: where its OAuth server is, the resource, and the scopes to ask for) and/or pasting a token (`token`). `identify` says who a credential is and what it may do (`ThirdPartyAbilities`: chat, see whether it's working, see and answer what's waiting); `create` makes the plugin, which reads its activity, its conversation and its requests, sends messages, and takes a request's actions. Connect (`apps/connect/src/third-parties.ts`) lists the plugins, and neither it nor the UI knows one from another.
- **In the data path:** unlike servers, Connect talks to a third party for the browser (`/v1/third-parties/*`), since their APIs are for servers (Revnu's sends no CORS headers). A credential is kept in D1 sealed with `THIRD_PARTY_KEY` (AES-256-GCM, with the row's id as additional data, so a sealed value copied onto another row won't open), and never reaches the browser. Without the key, third parties are off and Settings says so.
- **Signing in:** OAuth 2.1 as MCP servers do it, from `@nibblets/oauth` (which app links use too), said in third parties' errors by the base (`oauth.ts`): Connect reads the third party's metadata, registers itself as a public client for its callback address once (RFC 7591, kept in `third_party_clients`, and registered again if the third party forgets it), and sends the person to the authorize page with PKCE (S256) and a random state. The callback (`/v1/third-parties/callback`) is a plain page load, not signed in with Clerk, so it only keeps the code beside the sign-in (by a hash of its state, used once and good for ten minutes, in `third_party_sign_ins`) and sends the person to Settings with the state. There the UI finishes it (`/v1/third-parties/finish`), signed in, and only as whoever started it: otherwise someone could start signing in on their own account, send the link on, and get the access of whoever approved it. Finishing swaps the code for the token, asks the plugin who it is, and opens the new third party's page; anything that goes wrong is said in Settings. Connecting an account that's already connected (the same plugin and the third party's own id for it) replaces its credential rather than listing it twice, which is also how a revoked one comes back.
- **Renewing:** a plugin that asks for `offline_access` (Notra, whose access tokens last minutes) registers for the refresh grant too, and Connect keeps the refresh token sealed beside the credential (bound to `<id>:refresh`), with the client it belongs to and when the credential runs out. Within a minute of that, Connect renews it before handing it to the plugin. A refresh token can only be used once, and the UI asks several things at once, so one request claims the renewal (`renewing_until`, twenty seconds) and the rest use the old credential while it still works or wait for the new one. A refresh token the third party won't take marks the connection revoked. Plugins also get `waitUntil`, for reading a reply streamed back after the person has their answer.
- **Talking:** the page reads the conversation every six seconds while the third party is working or a message is on its way, and every thirty otherwise. A message carries a client id, so a retried send is sent once. The sidebar asks each third party what it's up to every thirty seconds, eight seconds at most each, and shows "Not answering" past that.
- **Requests:** what a third party is waiting on the person for (`ThirdPartyRequest`) is drawn from its actions alone: one primary, the rest beside it, each saying what it asks for (nothing, text, or one of some options) and what it does beyond the third party (`ships`: sends, publishes or spends; `answers`; `none`). One that ships, or asks for something, opens a step to fill in or confirm first. A request that can only be dealt with in the third party's own app has a link there.
- **Revoking:** a plugin throws `ThirdPartyRevokedError` when the third party stops taking a credential (Revnu's 401), and Connect marks it `revoked`: the sidebar says "Reconnect" and its page offers to connect it again. Forgetting one (Settings) deletes it from Connect; its access stays live in the third party until it's revoked there, which Settings says, since Revnu has no route for that.
- **Revnu** (`packages/third-party-revnu`): over Revnu's JSON API (`https://revnu.com/api/v1`, described by its OpenAPI document; there's no SDK). Signing in uses the OAuth its MCP server uses, which makes an `rvp_` personal token labelled with Connect's name in Revnu's Settings → Developers, asking for `agent:message`, `results:read`, `review:read` and `review:write`. A token pasted from there works too. Its conversation is that token's own (the dashboard's and Slack's aren't in it), and messages are queued rather than interrupting what Revnu is doing. Working is `GET /agent/status`, which covers the whole account. Requests are the review queue's cards, mapped as Revnu's review screen guide says: the main verb (send, approve, choose or answer, whichever it has first) under its `primaryLabel`, and approvals that publish, post, launch ads, raise the budget or buy domains marked as shipping. LinkedIn and gift cards can only be approved in Revnu's dashboard, so their main button is a link there. Its logo is Revnu's own favicon, a PNG.
- **Notra** (`packages/third-party-notra`): over Notra's REST API (`https://api.usenotra.com`, described by its OpenAPI document), with plain `fetch` rather than its SDK. Signing in uses the OAuth its MCP server uses (`https://oauth.usenotra.com`, for the resource `https://api.usenotra.com`), asking for `openid` and `offline_access`; the person picks a workspace and an access level there, and `GET /v1/me/workspaces` says which and the scopes that gave. An `ntra_` API key works too; it doesn't say its scopes, so connecting one checks it can read chats and finds out about writing when it tries. Its conversation is a chat of Nibblets' own per workspace, tagged with the external channel id `dashboard`/`nibblets` so it's found again, and shared by everyone who connects that workspace. Sending posts to it and reads the streamed reply to the end in the background. Notra has no idempotency key, so a send retried while Notra is still answering the same words is dropped. Chats come back as AI SDK UI messages, which the API leaves undescribed, so they're read leniently: text parts are the conversation, and the tool calls the latest reply waits on (`approval-requested`) are one request, since Notra takes all of a reply's approvals at once, with each tool's input as details. Allowing is marked as shipping, as those tools publish and change things. Working is the person having spoken last in the past ten minutes, or a tool still running; there's no status route. Its logo is Notra's own SVG favicon.

## Host tools (`packages/host-mcp`)

The host bridge runs on the host, in the desktop app (127.0.0.1:8789) or as `node packages/host-mcp/src/cli.ts --port 8789 --token <t> [--host 172.17.0.1]` on servers without it. The server reaches it at `HOST_MCP_URL` with `HOST_MCP_TOKEN`; empty turns it off. Nothing reaches a nibblet unless ticked for it.

- **Host MCP servers**: read in Claude's `mcpServers` format from `~/.nibblet/host-mcp.json`, then Claude Code's `~/.claude.json`, then Claude Desktop's config, with the first definition of a name winning. Each server is started on first use and served at `/mcp/<name>`; `GET /servers` lists them. A nibblet's `hostTools` names the ones it may use. Its runner registers each as `host_<name>` at the server's `/hostmcp/<name>`, which checks the nibblet's token and that list before forwarding.
- **Virtual machines**: the host's hypervisor plugin, at `/machines` (see [Machines](#machines-containers-and-virtual-machines)). The CLI keeps them in `~/.local/share/nibblets/machines` (`--machines`), the desktop app in its data directory.
- **CLI logins**: `CliPlugin`s (`gh` and `ssh` so far) detect whether a CLI is installed and signed in (`GET /clis`) and turn its login into environment variables (`GET /clis/:id/credential`). For each CLI in a nibblet's `cliCredentials`, the server fetches a fresh credential on every configure and sends it only over the runner socket. The runner puts it in the harness's environment and runs the CLI's setup (`gh auth setup-git`). It is never stored, logged, or returned by the API.
- **SSH keys**: the `ssh` plugin shares the host's SSH agent, never a key. It's offered when `ssh-add -l` lists keys. For a nibblet that has it ticked, the server bind-mounts `HOST_SSH_AUTH_SOCK` (`/run/host-services/ssh-auth.sock` on Docker Desktop and OrbStack, the host's `$SSH_AUTH_SOCK` on Linux) at `/run/nibblet/ssh-agent.sock`. Because it's a mount, ticking or unticking it restarts the container. On Linux the socket is usually `0600`, owned by the host user, so the container's `nibblet` user (uid 1001) can't open it unless the uids match.
- **A nibblet's own MCP servers** (`mcpServers`): remote URLs, or commands run inside its container by the guard. Header and env values are secrets: the API returns them as `••••`, an update that sends `••••` back keeps the stored value, and only the guard receives them.
- **Host tool approvals**: `/hostmcp/<name>` reads each request before forwarding it, and refuses batches and anything it can't read, so an "ask me first" host tool can't be called without asking.

Shared memories are written to the system prompt only when they're the nibblet's own. Other nibblets' shared notes come back from `memory_search` marked as information, not instructions.
